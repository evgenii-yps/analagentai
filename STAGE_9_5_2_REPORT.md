# Этап 9.5.2 — запись демо-сделок в лист владельца «торговля демо апи окх»

Репозиторий evgenii-yps/analagentai, ветка `claude/wonderful-volta-x9b0a3`, основа — main `1cab06b` (PR #15).
Система вписывает в лист владельца только исходные данные демо-сделок; выручку, прибыль, %, баланс и лист
«баланс демо апи окх» считают формулы владельца. Включается `DEMO_OWNER_SHEET_ENABLED=true` (по умолчанию `false`).
`DEMO_SHEETS_ENABLED` остаётся `false`: листы «Демо OKX — сделки / баланс по дням» остались в коде и не включены.

### Приёмник, режим `cells_values`
Лист ищется по `trim(имя)` (точное сравнение после trim с обеих сторон): 0 совпадений → `sheet_not_found`, больше одного →
`sheet_ambiguous`; **лист не создаётся никогда**. До первой записи проверяются ВСЕ диапазоны `writes` и `clears`:
форма адреса (только `A3` / `A6:D40`; чужие листы и целые столбцы — `bad_range`), размер значений (`values_shape`),
выход за пределы листа (`range_out_of_sheet`), строки-«формулы» в значениях (`formula_in_values`) и `getFormulas()`
(`formula_in_target` с адресом диапазона) — при любом отказе не записано ничего. Запись — `setValues`, очистка —
`clearContent` (не `clear`, не `clearFormat`). Ответ `{ok:true, written, cleared, version}`.

### Строки листа (колонки A–D, F–K, M, T; A3 — стартовый капитал)
* Блоки записи `A:D`, `F:K`, `M`, `T`; колонки E, L, N–S, U, V ни в одном диапазоне не встречаются (тест 1).
* Куплена: A/B — дата/время `buy.filled_at` числами (дни от 30.12.1899 / доля суток, по `NOTIFY_TIMEZONE`), C — токен,
  D — «покупать», F/G — цена и сумма покупки; H–K — только после продажи; M — вся комиссия в $; T — заметка.
* **K и M**: `K = sell.cost_usd + fee_qty_покупки × sell.avg_price`, `M = комиссия покупки в $ + комиссия продажи в USDT`
  (непроданная: комиссия монеты × `buy.avg_price`). Тогда формула владельца `N = (K − G) − M` равна
  `ledger.pair_profit` — тому, что показывает `/demo` и на чём держится `cash`.
* Не куплена: A/B = `positions.opened_at`; D — «пропущено» / «ошибка» / «потеряна»; ордер в пути — «покупать»;
  заметки по ТЗ §3.4–3.5.
* Каждый прогон перестраивает область целиком и очищает хвост (последняя записанная + 1 … `DEMO_OWNER_SHEET_LAST_ROW`)
  в тех же четырёх блоках; в базе меток нет.

### Запуск и защита
* `_export_demo_owner_sheet` вызывается в КАЖДОМ прогоне (полном и `--positions-only`), не бросает исключений, не
  останавливает остальные цели. Выключено — ни запроса к базе, ни обращения к сети.
* Перед записью — запрос `version`. Версия ≠ `9.5.2` (или нет ответа) → записи нет, алерт «приёмник Google не обновлён
  до 9.5.2» (антидребезг 1 ч, Redis `SET NX EX`). Отказ записи (`sheet_not_found`, `formula_in_target`, сеть) — тоже
  алерт с антидребезгом 1 ч по коду причины. Строки кончаются (позиций > `LAST_ROW − 15`, и при > `LAST_ROW − 5` лишние не
  пишутся) — алерт «в листе кончаются строки с формулами, протяните формулы ниже», антидребезг 24 ч.
* Журнал: одна строка на успешный прогон — `demo_owner_sheet_done=1 rows= written= cleared= version= seconds=`.
  Отметка последнего успеха — Redis `export:demo_owner_sheet:last_ok` (читает `verify_9_5.sh`).

## Расхождения с ТЗ и находки (прошу решения владельца там, где указано)

1. **Версия приёмника 9.5.2 против журнала, требовавшего «ровно 9.2».** Клиент журнала сравнивал версию на точное
   равенство с `9.2`, и четыре старых теста закрепляли строку `'9.2'` в приёмнике. Подъём `RECEIVER_VERSION` до 9.5.2 без
   правки клиента остановил бы выгрузку в действующий журнал в момент обновления приёмника. Сделано: журнал принимает
   обе версии (членство в кортеже `_TRADES_COMPATIBLE_VERSIONS = ("9.2", "9.5.2")`, сравнение остаётся точным, а не «не
   меньше»); 9.5.2 — надмножество 9.2, режимы журнала побуквенно те же. Поведение журнала для владельца не изменилось.
2. **`rules.pair_pnl` и комиссия покупки в USDT.** ТЗ требует `(K − G) − M = pair_pnl` «до 1e-6» и одновременно
   «Σ по закрытым = изменение cash в ledger». Для комиссии покупки в МОНЕТЕ (реальный случай спота OKX) это одно и то же.
   Для комиссии покупки в USDT `rules.pair_pnl` её не вычитает, а `ledger.pair_profit` и `cash` — вычитают, и `M` по ТЗ
   включает её «как есть». Лист подчинён ДЕНЬГАМ (`ledger` / `/demo`), поэтому для USDT-комиссии `N = pair_pnl − fee_buy`.
   Тест 3 проверяет обе связи (и именно эту разницу). Код `src/demo/rules.py` не менялся — решение о выравнивании
   `pair_pnl` за архитектором.
3. **Колонка D с проверкой данных «покупать, пропущено».** На стенде (двойник книги) `setValues` пишет «ошибка»,
   «потеряна» и проверку не трогает; приёмник нигде не вызывает API проверки данных (двойник бросает ошибку при попытке).
   Но двойник повторяет ДОКУМЕНТИРОВАННОЕ поведение Google (запись из скрипта проверку не применяет) — на живой книге
   это подтвердит только первая запись: п. 8 инструкции ниже. Если Google всё же отвергнет значения — доложить; проверку
   данных я не меняю.
4. **«по цене демо-рынка» в заметке открытой позиции.** Текст фиксирован ТЗ. Цена берётся «как в ledger.py»: у службы
   export нет клиента демо-биржи, поэтому это последняя закрытая минутная свеча `ohlcv` (тот же запасной путь, что в
   `ledger.value_legs`). Нет свечи — «текущая прибыль: нет цены».
5. **Заметка «ОРДЕР ОТПРАВЛЕН»** записана буквально по ТЗ, без метки `[поз. N]` (у остальных статусов метка есть).
6. **Пояснение к коду ошибки OKX** берётся из собственной таблицы (`51008`, `51020`, `51000`…, иначе «отказ биржи»), а не из
   `error_text`: сырой текст биржи приходит извне, и «без ключей, подписей и заголовков» гарантируется тем, что в T попадает
   только наш текст (тест 11).
7. **Алерты этой цели идут мимо общего алерта выгрузки** и не поднимают код выхода: общий уходил бы каждые 15 минут при
   одной и той же причине (например, необновлённый приёмник), а ТЗ требует антидребезг. Остальные цели работают как раньше.
8. **Имя листа в запросе `version`** — «торговля тест апи окх чтение» (старый лист, существует точно), а не лист
   владельца: приёмник до 9.1.2 на неизвестный режим создаёт лист с переданным именем, а точное имя листа владельца (с
   пробелом в конце) клиенту неизвестно. Развёрнутый приёмник (≥ 9.2, раз журнал с ним работал) режим знает.
9. В шапке `deploy/apps_script.gs` (унаследованной) инструкция называет книгу «Analitik Agent», в ТЗ — «Agent Trade».
   Не менял; прошу подтвердить, в какой книге живёт скрипт.

## Инструкция владельцу

**A. Обновить приёмник в Google** (код живёт на стороне Google и не обновляется вместе с контейнером):

1. Открыть книгу со скриптом (см. п. 9 выше) → **Расширения → Apps Script**.
2. Выделить весь код (Ctrl+A), удалить и вставить содержимое файла `deploy/apps_script.gs` из ветки этого PR.
3. Заменить `ВСТАВЬ_СЮДА_СЕКРЕТ` на **тот же** секрет, что был (это `SHEETS_SHARED_SECRET` из `.env` на сервере). Забытый
   секрет — самая частая ошибка: выгрузка начнёт отвечать `forbidden`.
4. Сохранить (Ctrl+S) → **Развернуть → Управление развёртываниями** → значок **карандаша (Изменить)** →
   **Версия: «Новая версия»** → **Развернуть**. Адрес `/exec` не меняется, `.env` трогать не нужно.
5. **Проверить версию командой на сервере** (секрет читается из `.env`, в команде его нет):

   ```bash
   cd /opt/agent-trade
   URL=$(grep -E '^SHEETS_WEBAPP_URL=' .env | cut -d= -f2- | sed 's/[[:space:]]*#.*//')
   SECRET=$(grep -E '^SHEETS_SHARED_SECRET=' .env | cut -d= -f2- | sed 's/[[:space:]]*#.*//')
   curl -sL -X POST "$URL" -H 'Content-Type: application/json' \
     -d "{\"secret\":\"$SECRET\",\"mode\":\"version\",\"sheet\":\"торговля тест апи окх чтение\"}"
   ```

   Ожидаемый ответ: `{"ok":true,"version":"9.5.2"}`. Другая версия — п. 4 не выполнен («Новая версия» не выбрана).

**B. Включить запись** (после слияния PR и обновления кода на сервере; до п. 5 включать нельзя только в том смысле, что
запись просто не произойдёт и придёт алерт):

6. В `.env`: `DEMO_OWNER_SHEET_ENABLED=true` (`DEMO_OWNER_SHEET` и `DEMO_OWNER_SHEET_LAST_ROW=1000` уже по умолчанию).
   Контейнеры перезапускать не нужно — `export` запускается разово из cron и читает `.env` при каждом запуске.
7. Первый запуск вручную:
   `docker compose --profile tools run --rm --no-deps export python -m src.export_main --positions-only`
   В журнале — строка `demo_owner_sheet_done=1` с `rows`, `written`, `cleared`, `version=9.5.2`.
8. Проверка на листе: **A3** = стартовый капитал; каждая демо-позиция — строка со строки 6, старые сверху; в колонке **D**
   у строк «ошибка» / «потеряна» значения записаны (проверка данных не помешала; если помешала — сообщить мне, не менять);
   прибыль в **N** совпадает с `/demo` по закрытым сделкам; формулы и оформление на месте; лист «баланс демо апи окх»
   считает от новых строк.
9. Повторный запуск (п. 7) без новых сделок ничего не меняет.
10. `sudo -u agent bash /opt/agent-trade/deploy/verify_9_5.sh` — пункт 10 показывает `DEMO_OWNER_SHEET_ENABLED` и время
    последнего успешного прогона.

Если строки с формулами подходят к концу (строка 985+), придёт алерт «протяните формулы ниже»; формулы протягивает
владелец, после этого `DEMO_OWNER_SHEET_LAST_ROW` поднимается в `.env` до новой последней строки с формулами.
