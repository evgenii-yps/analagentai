### 0.3 Границы применимости замеров: что закрыто, а что нет

**Все измерения этого отчёта сделаны на стенде, а не на продакшн-сервере.**
Среда разработки закрыта сетевой политикой: `CONNECT` к `www.okx.com`,
`api.binance.com` и любой другой бирже возвращает HTTP 403. Поэтому живой стек
прогонялся против ЛОКАЛЬНОГО ЗАМЕНИТЕЛЯ OKX, отвечающего теми же эндпоинтами
(`/api/v5/public/instruments`, `/market/candles`, `/market/books`,
`/market/trades`, `/public/funding-rate`, `/public/open-interest`,
`/market/ticker`) в том же формате. Код проекта обращается к нему как к бирже —
по адресу `https://www.okx.com`, без единой правки в коллекторах.

Ни одно из этих чисел не относится к Hetzner CX23:

* **темп записи сделок** (2.8 млн строк в сутки на токен) — упирается в потолок
  заменителя: он отдаёт 500 сделок на запрос, коллектор опрашивает раз в 15
  секунд. Разницы между DOGE, XRP и BTC стенд дать не может — там, где вы
  ожидаете разные частоты, у него заглушка;
* **задержка ответа биржи** (медиана 3 мс, 95-й процентиль 249 мс) — это
  локальный сервер в той же сети докера, а не биржа через интернет;
* **процессор и память** — машина 16 ГБ / 4 ядра, а не CX23;
* **свободное место 70%** — диск этой машины 252 ГБ, а не 37.21 ГБ сервера;
* **длительность прогона — 35 минут** вместо двух часов, требуемых §2 ТЗ.

**Поэтому критерии приёмки §11.2 и §11.3 НЕ ЗАКРЫТЫ.**

| Критерий | Состояние |
|---|---|
| §11.2 Два токена отработали 2 часа, замеры приложены, пороги не нарушены | **НЕ ЗАКРЫТ.** Механизм замеров проверен на стенде (§12), двухчасовой прогон на сервере не выполнялся |
| §11.3 Пять токенов отработали 2 часа, замеры приложены | **НЕ ЗАКРЫТ.** На стенде состав на пять не переключался: это ничего не измерило бы |

Оба критерия закрываются ТОЛЬКО прогоном на продакшн-сервере, в порядке §2 ТЗ:
два токена → два часа → замеры → пять токенов → два часа → замеры. Команды — в
§13 этого отчёта.

Что стенд доказал и что переносится на сервер без оговорок: правильность
кода (разведение рынков, четыре горизонта, границы версий, свёртки и сроки
хранения), работоспособность самих скриптов замера и проверки, и темп обращений
к бирже — он задан интервалами конфигурации, а не рынком (26 запросов в минуту
на два токена, ожидаемые ~65 на пять).

## 1. Инструменты: пять токенов, два рынка у каждого (§1)

### 1.1 Что установлено замерами и как это отражено в коде

Замеры 22.08.2026, приведённые в ТЗ, подтверждены строением кода: Market Agent
работает на СПОТЕ, Futures Agent — на КОНТРАКТЕ, свечи собираются только по
споту, funding и открытый интерес — только по контракту. Поэтому инструмент
системы — это ПАРА рынков, и задаётся она явно:

```
SYMBOLS=BTC/USDT:BTC/USDT:USDT,ETH/USDT:ETH/USDT:USDT,SOL/USDT:SOL/USDT:USDT,\
XRP/USDT:XRP/USDT:USDT,DOGE/USDT:DOGE/USDT:USDT
```

Разделитель пары — **первое** двоеточие: имя бессрочного контракта на OKX само
содержит двоеточие (`BTC/USDT:USDT`), и разбор по последнему разделителю
разорвал бы его. Достраивание имени контракта из имени спота запрещено и не
выполняется нигде (`src/core/instruments.py`): имена инструментов принадлежат
бирже, а не нашим соглашениям. Пара без контракта — ошибка конфигурации, и
сервис не стартует.

Пустой `SYMBOLS` означает одну пару из `SYMBOL`/`SWAP_SYMBOL` — поведение до
Этапа 8.1. Это нужно, чтобы обновление кода без правки `.env` ничего не меняло.

### 1.2 Где раскатан состав

| Файл | Что стало |
|---|---|
| `src/core/instruments.py` | новый модуль: разбор пар, регистрация инструментов, разбор горизонтов |
| `src/collectors/runner.py` | по комплекту из четырёх коллекторов на каждую пару |
| `src/agents/runner.py` | по три агента на пару: Market и Liquidity — спот, Futures — контракт |
| `src/decision/runner.py` | по одному Decision Agent на пару; сигнал пишется под инструментом спота |
| `src/core/db.py` | независимость наблюдений считается ПО ТОКЕНУ (иначе четыре пятых данных исчезали бы) |

### 1.3 Наблюдаемость пяти токенов без поломки надзора

Имя агента осталось плоским (`market`, `liquidity`, `futures`): по нему
Decision Agent ищет выводы, по нему настроены веса, оно лежит в
`agent_outputs.agent`. Токен различает экземпляры там, где это нужно, —
в ключах Redis и в полях лога.

Heartbeat пишется ДВУМЯ ключами: общий (`agent:heartbeat:market`) обновляет
любой токен — его читают вотчдог, бот и суточная сводка; ключ с токеном
(`agent:heartbeat:market:BTC`) показывает, какой именно экземпляр отстал.
Переименовать общий ключ было нельзя: вотчдог счёл бы его пропажу отказом и
начал бы перезапускать живой контейнер.

Счётчик серии сбоев, наоборот, теперь пер-токенный: иначе сбои одного токена
засчитывались бы другому и алерт срабатывал бы не на том.

## 2. Четыре горизонта оценки (§5)

### 2.1 Схема

Миграция `db/migrations/009_stage_8_1_horizons.sql` (откат —
`..._rollback.sql`) добавляет `horizon_h SMALLINT NOT NULL`, снимает прежний
суррогатный первичный ключ и уникальность по текстовому горизонту, ставит
`PRIMARY KEY (signal_id, horizon_h)` и индекс `ix_eval_horizon`.

**Отклонение от буквы ТЗ, сделанное сознательно.** §5 предписывает
`UPDATE signal_evaluations SET horizon_h = 4 WHERE horizon_h IS NULL`.
Буквальное применение сломало бы данные: в таблице есть строки с
`horizon = '1h'` — они считались НА ЧАСЕ, и объявить их четырёхчасовыми значит
подменить факт (а две такие строки одного сигнала ещё и столкнулись бы на новом
первичном ключе). Поэтому горизонт берётся из уже записанного текста
(`'1h'` → 1, `'4h'` → 4), и только неразбираемое значение получает 4. Смысл
требования — «не выдумывать горизонтов задним числом» — соблюдён строго: ни
одной НОВОЙ строки миграция не создаёт.

Текстовая колонка `horizon` сохранена и заполняется подписью того же значения
(`4` → `'4h'`): её читают выгрузка, бот и суточная сводка, и ломать их ради
переименования незачем.

**Защита, найденная проверкой миграции на старой схеме.** Если в колонке
`horizon` когда-то оказалось значение, которое не разбирается, оно получает 4
по правилу ТЗ — и сталкивается с настоящей строкой `'4h'` того же сигнала.
Первая редакция миграции падала на этом с сообщением
`could not create unique index`, которое дежурному ничего не объясняет.
Теперь миграция останавливается САМА, называет конкретные `signal_id` и
говорит, что делать. Молча удалить лишнюю строку она не имеет права: какая из
двух оценок верна — решать не миграции. Та же защита стоит в
`db.ensure_evaluator_schema` (сервис на старом томе приводит схему сам).

Миграция проверена на копии СТАРОЙ схемы: применяется, повторное применение
проходит без ошибок и без изменений, откат возвращает прежний ключ.

### 2.2 Запрет досчёта задним числом (§12)

Сигналам, выданным ДО перехода на текущую версию логики, новые горизонты не
считаются. Граница берётся из таблицы `logic_version_windows` (§6).

Здесь найдена и закрыта дыра, которой в ТЗ нет. Первая редакция читала границу
из БД, а записывал её только Decision Agent. Порядок старта контейнеров не
задан: если оценщик поднимался раньше, он получал «границы нет» — то есть
работал БЕЗ отсечения и досчитал бы горизонты 12ч и 24ч старым сигналам версии
4. Теперь границу ЗАПИСЫВАЕТ тот сервис, который стартовал первым (запись
идемпотентна, первый писатель побеждает), поэтому «границы нет» не бывает.

### 2.3 Независимость горизонтов

Каждый горизонт считается своей выборкой: сигналу пять часов — оценены 1ч и 4ч,
12ч и 24ч ждут своего времени и не мешают остальным. Сигнал при этом ОДИН, и
закрывается он один раз — по главному горизонту (`EVAL_PRIMARY_HORIZON=4`).

## 3. Версия логики и граница данных (§6)

`LOGIC_VERSION` поднят с 4 до 5. Момент границы фиксируется в БД с точностью до
минуты при первом старте на версии:

```
logic_version | started_at
            4 | 2026-08-16 16:25:00+00   (перенесено из отчёта 7.4 §13.2)
            5 | <момент развёртывания>   (пишется автоматически)
```

Запись делается один раз (`ON CONFLICT DO NOTHING`): перезапуск сервиса границу
не сдвигает, иначе «начало версии» уезжало бы вперёд и данные до перезапуска
выпадали бы из окна анализа.

## 4. Срок хранения и объём БД (§4 ТЗ и решение заказчика по §4.3)

### 4.1 Измеренный темп записи сделок

Сначала измерение, потом расчёт. Фактический темп на работающем стеке, по
каждому токену отдельно (окно 34.7 минуты, приведено к суткам):

| Инструмент | Строк за окно | Строк в минуту | Строк в сутки |
|---|---|---|---|
| BTC/USDT | 67 436 | 1 943 | **2 797 798** |
| ETH/USDT | 68 080 | 1 962 | **2 824 795** |

Команда, которой это снято (её же надо выполнить на сервере — там числа будут
другими):

```sql
SELECT i.symbol, count(*) AS строк,
       round(count(*) * 86400.0 /
             GREATEST(extract(epoch FROM (max(t.ts)-min(t.ts))), 1)) AS строк_в_сутки
  FROM trades t JOIN instruments i ON i.id = t.instrument_id
 WHERE t.ts > now() - interval '24 hours'
 GROUP BY i.symbol ORDER BY i.symbol;
```

**Что эти числа значат и чего не значат.** 2.8 млн строк в сутки — это ПОТОЛОК
КОЛЛЕКТОРА, а не частота рынка: заменитель биржи отдаёт по 500 сделок на
запрос, коллектор опрашивает раз в 15 секунд, 4 × 500 × 1440 = 2.88 млн. Оба
токена уткнулись в одно и то же значение именно поэтому, и разницы между
токенами здесь нет — на настоящей бирже она будет.

Верхняя граница по конструкции на настоящей OKX: `limit=1000` каждые 15 секунд
= **5.76 млн строк в сутки на токен**. Больше коллектор физически не запишет.
Реальный темп у DOGE и XRP отличается от BTC — какой именно, покажет тот же
запрос на сервере.

### 4.2 Решение по §4.3: двое суток сырья, итоги минут навсегда

| Таблица | Срок | Настройка |
|---|---|---|
| `trades` (сырая лента) | **2 суток** | `RETENTION_TRADES_DAYS=2` |
| `trade_flow_1m` (итоги минут) | **не удаляется никогда** | — |
| `agent_outputs` (журнал выводов) | 90 суток | `RETENTION_AGENT_OUTPUTS_DAYS=90` |
| `agent_outputs_daily` (итоги суток) | **не удаляется никогда** | — |
| `orderbook_snapshots` | 14 суток | `RETENTION_ORDERBOOK_DAYS=14` |
| `ohlcv` только `timeframe='1m'` | 30 суток | `RETENTION_1M_DAYS=30` |
| часовые (и любые не 1m) свечи, `funding`, `open_interest`, `signals`, `signal_evaluations`, `trade_flow_1m`, `agent_outputs_daily` | не удаляются никогда | — |

Обе свёртки устроены одинаково и по одной причине: сырьё нужно для разбора
инцидентов, содержательная часть — навсегда.

Таблица итогов (миграция `010_trade_flow_1m.sql`):

```sql
CREATE TABLE trade_flow_1m (
    instrument_id INTEGER       NOT NULL REFERENCES instruments(id),
    ts            TIMESTAMPTZ   NOT NULL,
    trades_n      INTEGER       NOT NULL,
    buy_volume    NUMERIC(30,8) NOT NULL,
    sell_volume   NUMERIC(30,8) NOT NULL,
    buy_n         INTEGER       NOT NULL,
    sell_n        INTEGER       NOT NULL,
    vwap          NUMERIC(20,8) NOT NULL,
    PRIMARY KEY (instrument_id, ts)
);
```

Свойства свёртки, обеспеченные кодом (`scripts/retention.py::rollup_sql`):

* **Сначала свёртка, потом удаление.** Порядок не «по договорённости», а
  проверяемый: если свёртка не удалась, правило удаления `trades`
  ПРОПУСКАЕТСЯ с явной строкой в логе. Потерять сырьё, не сохранив итог,
  нельзя; отложить удаление на сутки — можно.
* **Незавершённая минута не сворачивается.** Граница —
  `date_trunc('minute', now())` минус запас `ROLLUP_LAG_MINUTES` (5 минут):
  коллектор опрашивает биржу раз в 15 секунд, и хвост только что закончившейся
  минуты может быть ещё не записан. Свернуть её раньше времени значит
  зафиксировать неполный итог.
* **Идемпотентность.** `ON CONFLICT DO NOTHING`: повторный запуск не создаёт
  дублей и НЕ МЕНЯЕТ уже записанные значения. Именно «не меняет», а не
  «пересчитывает»: пересчёт по частично удалённому сырью испортил бы верный
  итог.
* **Суммы точные.** Объём и цена суммируются в `numeric`, а не в
  `double precision`.
* Сделки без указанной стороны считаются в `trades_n` и участвуют в VWAP, но не
  попадают в объёмы по сторонам: приписать их произвольной стороне значило бы
  выдумать данные. Их число печатается в логе свёртки.

### 4.3 Свёртка ленты сделок на живых данных

Свёртка 157 424 строк сырья двух токенов, выполненная настоящей ежесуточной

```
            68 |                    0 |               0 |                0 |                 0

  symbol  | минут | сделок_в_итогах | сделок_в_минуту | средний_vwap
```

Удаление сырья не меняет итоги (слепок md5 по всем строкам до границы

Размер: 157 424 строки сырья свернулись в **70 строк итогов (40 КБ)**.

Инкрементальная свёртка на живом прогоне (задача запущена повторно через
21 минуту, когда накопились новые сделки):

```
[19:25:54] trade_flow_1m: свёрнуто минут (новых строк): 28; всего строк итогов: 98.
           Запас свёртки: 5 мин.
```

Уже записанные 70 строк при этом не изменились — тот же слепок md5 до и после:

```
до:    70 строк, md5=04747eb4cb2dd19e6e47f2f3f04b6883
после: 70 строк, md5=04747eb4cb2dd19e6e47f2f3f04b6883
```

Новые 28 минут сверены с сырьём: расхождений по числу сделок и по объёму —
ноль. То есть свёртка добавляет новое, не трогая старое, — ровно это и значит
«идемпотентна» в требовании.

### 4.4 Суточная свёртка выводов агентов

Журнал `agent_outputs` живёт 90 суток, суточные итоги — навсегда (миграция
`011_agent_outputs_daily.sql`). Устройство то же, что у ленты сделок: свёртка
идёт по ЗАВЕРШЁННЫМ суткам, ДО удаления сырья, идемпотентна, и при неудаче
свёртки удаление журнала пропускается.

**Откуда берётся `logic_version`.** В самой таблице `agent_outputs` его нет, и
добавлять задним числом нельзя: у старых строк верного значения взять неоткуда.
Версия восстанавливается по окнам `logic_version_windows` (§6): для вывода в
момент `ts` берётся последнее окно, начавшееся не позже `ts`. Выводы раньше
самой ранней ЗАПИСАННОЙ границы получают `logic_version = 0` — признак «версия
неизвестна», и их число печатается отдельной строкой в логе.

> ИСПРАВЛЕНО ПОСЛЕ ДЕФЕКТА НА СЕРВЕРЕ 22.08.2026. В первой редакции таким
> выводам подставлялась минимальная известная версия, и 33 895 выводов версий
> 1-3 были записаны в вечную таблицу как версия 4. Разбор, исправление уже
> записанного и проверки — §15.

**`repeat_rate`** — доля ПОЛНЫХ повторов: вывод считается повтором, когда с
предыдущим выводом того же агента по тому же инструменту совпали И направление,
И уверенность (до четвёртого знака) — так эта величина считалась в Расчёте 4
диагностики 7.1. Сравнение идёт по всему ряду, а не внутри суток: первая запись
суток сравнивается с последней записью предыдущих, иначе каждый день терял бы
одно сравнение. Если сравнивать не с чем вовсе (единственный вывод за сутки),
доля равна нулю.

**`n_total`** считает ВСЕ выводы суток, включая `insufficient_data`, поэтому
сумма трёх направлений может быть меньше `n_total`. Это не расхождение:
«агенту не хватило данных» — не направление.

Фактический прогон на живом стеке (задача та же, ежесуточная):

```
[22:30:16] agent_outputs_daily: свёрнуто суток (новых строк): 12; всего строк итогов: 12.

    day     |   agent   |     токен     | версия | n_total | n_bullish | n_bearish | n_neutral | conf_avg | conf_p90 | repeat_rate
 2026-08-19 | futures   | BTC/USDT:USDT |      4 |      78 |         0 |         0 |         0 | 0.000000 | 0.000000 |      1.0000
 2026-08-19 | liquidity | BTC/USDT      |      4 |      78 |         1 |         0 |        76 | 0.054009 | 0.081720 |      0.0779
 2026-08-19 | market    | BTC/USDT      |      4 |      78 |        42 |         0 |        35 | 0.416451 | 0.745100 |      0.9610
 2026-08-19 | market    | ETH/USDT      |      4 |      78 |        35 |        42 |         0 | 0.631313 | 0.842000 |      0.9610
```

У `futures` все 78 выводов — `insufficient_data` (истории funding за неделю на
стенде нет), поэтому три направления нулевые при `n_total = 78`, а
`repeat_rate = 1.0`: агент повторял один и тот же вывод. Ровно тот случай,
ради которого `n_total` считает всё, а не только направления.

**Сутки на границе версий дают ДВЕ строки.** Проверено на живых данных: граница
версии 5 сдвинута на 21:00 предыдущих суток —

```
    day     | agent  |  токен   | версия | n_total | repeat_rate
 2026-08-21 | market | BTC/USDT |      4 |      72 |      0.9444
 2026-08-21 | market | BTC/USDT |      5 |       6 |      1.0000
 2026-08-21 | market | ETH/USDT |      4 |      72 |      0.9444
 2026-08-21 | market | ETH/USDT |      5 |       6 |      1.0000
```

Смешанной строки не возникает ни при каком расположении границы.

Тесты (10 проверок на настоящей PostgreSQL,
`tests/test_agent_outputs_daily.py`): точность счётчиков и уверенности,
`repeat_rate` считает только полные повторы, разделение по агентам и
инструментам, две строки на границе версий, незавершённые сутки не
сворачиваются, идемпотентность, удаление сырья не меняет итоги, сравнение через
границу суток, единственный вывод даёт нулевую долю повторов.

Два дефекта, найденных этими тестами и исправленных: `percentile_cont`
возвращает `double precision` даже для `numeric` (нужен явный привод, иначе
`round(double, int)` не существует), и при единственном выводе за сутки
`repeat_rate` получался пустым при `NOT NULL`-колонке.

### 4.5 Кто читает сырую ленту (пункт 3 решения)

Проверено сплошным поиском по коду. **Ни один агент, ни выгрузка, ни

### 4.7 Что пришлось изменить сверх решения — и почему

Расчёт показал: даже при сроке сделок в трое суток порог 40% на горизонте года
на диске 40 ГБ не выполнялся бы **из-за журнала выводов агентов**
(`agent_outputs`) — 6.6 ГБ в год на пять токенов, больше всех «вечных» таблиц
вместе взятых.

Этой таблицы НЕТ в перечне §4 ТЗ 8.1 («часовые свечи, funding, открытый
интерес, сигналы и оценки не удаляются никогда») — в защищённые её включил я
сам, из перестраховки. Поэтому ей задан срок хранения 90 суток
(`RETENTION_AGENT_OUTPUTS_DAYS`, значение 0 отключает правило). Что при этом
теряется и что нет:

* **не теряется:** мнения агентов, УЧАСТВОВАВШИЕ В РЕШЕНИИ, — они хранятся
  навсегда в `signals.agents_payload`, вместе с самим сигналом;
* **теряется старше 90 суток:** детальные метрики агентов (RSI, EMA,
  перцентили funding) — они нужны для разбора «почему агент так решил», а не
  для анализа результатов.

Читают `agent_outputs` только бот (последние выводы) и аналитические запросы
`analysis/sql/*` за окна в недели — 90 суток им хватает с запасом.

Если это решение не устраивает — верните `RETENTION_AGENT_OUTPUTS_DAYS=0`
(журнал не будет удаляться) и заложите +5 ГБ в год на пять токенов.

## 5. Незавершённый бар (§8)

Введена настройка `MARKET_CLOSED_BARS_ONLY`, по умолчанию **false**. При false
поведение системы не меняется НИ В ЧЁМ: функция отсечения не вызывается вовсе,
окно Market Agent остаётся тем же, что и до Этапа 8.1, включая недосчитанный
последний бар. При true из окна исключается бар, который ещё не закрылся
(`ts + длительность > сейчас`).

Значение в этом этапе не менялось — так и требует ТЗ. Переключатель введён,
чтобы эффект можно было измерить отдельным этапом, а не чтобы применить сейчас.

Тонкость границы: бар 17:00 при часовом таймфрейме закрыт РОВНО в 18:00:00, а не
в 18:00:01 — на этом стоит отдельный тест. Незнакомый таймфрейм не даёт повода
угадывать длительность бара: отсечение просто не выполняется, и данные не
теряются.

## 6. Выгрузка независимых окон (§7)

Лист «Независимые окна» пересобирается по одному наблюдению НА ТОКЕН И НА
ГОРИЗОНТ: окно равно длине горизонта, из окна берётся первый по времени сигнал.
Ключ прореживания включает инструмент — без него пять токенов делили бы одно
окно и четыре пятых наблюдений исчезли бы молча.

Первой строкой листа выводится обязательная оговорка §7:

> ВНИМАНИЕ: пять токенов НЕ дают пятикратного роста статистической мощности.
> Криптовалюты сильно коррелированы: одно и то же движение рынка попадает в
> наблюдения по всем токенам сразу. Фактическая корреляция исходов между
> токенами приведена в колонке «корреляция с другими токенами» и на листе
> «Корреляция токенов»; эффективное число независимых наблюдений МЕНЬШЕ
> формального.

Рядом с каждым наблюдением стоит колонка «корреляция с другими токенами» —
средняя корреляция исходов этого токена с остальными на том же горизонте.
Отдельный лист «Корреляция токенов» даёт попарные значения: горизонт, пара
токенов, число совпавших окон и коэффициент корреляции попаданий. Пустое
значение означает «не измерено» (мало совпавших окон), а не «ноль»: это разные
утверждения, и подменять одно другим нельзя.

Та же поправка внесена в независимость наблюдений для КАЛИБРОВКИ
(`db.get_independent_outcomes`): прореживание считается по токену, иначе кривая
строилась бы по пятой части данных.

Требование «считается ежесуточно» выполняется существующим расписанием: выгрузка
запускается из cron ежедневно в 06:20 UTC (`deploy/install.sh`, строка уже
стоит), и оба служебных листа пересобираются целиком при каждом запуске.

Фактическая проверка на работающей базе (запрос выполнен тем же кодом, что
использует выгрузка):

```
ЛИСТ «Независимые окна»: наблюдения разведены по токену И горизонту
  горизонт_ч | токен | окно_utc                  | signal_id | decision
  1          | BTC   | 2026-08-21T12:00:00+00:00 | 9         | buy
  1          | ETH   | 2026-08-22T13:00:00+00:00 | 10        | sell
  4          | BTC   | 2026-08-21T12:00:00+00:00 | 9         | buy
  4          | ETH   | 2026-08-22T12:00:00+00:00 | 10        | sell
  12         | BTC   | 2026-08-21T12:00:00+00:00 | 9         | buy
  24         | BTC   | 2026-08-21T00:00:00+00:00 | 9         | buy

ЛИСТ «Корреляция токенов»
  горизонт_ч | токен_a | токен_b | N совпавших окон | корреляция исходов r
  1          | BTC     | ETH     | 6                | 1.0

```

Значение r = 1.0 здесь принадлежит ЗАМЕНИТЕЛЮ биржи (ряды двух токенов в нём
почти синхронны), а не рынку. Важно другое: механизм считает корреляцию на
совпавших окнах и оставляет ячейку пустой там, где окон слишком мало, — «не
измерено» и «ноль» не подменяются друг другом.

## 13. Развёртывание на сервере: порядок команд

Порядок обязателен: §2 ТЗ запрещает включать пять токенов, минуя проверку на
двух. Двухчасовые прогоны (§11.2 и §11.3) закрываются здесь и только здесь —
на стенде они не выполнены (§0.3).

### Шаг 1. Обновить код

```bash
cd /opt/agent-trade
sudo -u agent git pull
```

### Шаг 2. Применить миграции — строго в этом порядке

```bash
cd /opt/agent-trade
for m in 009_stage_8_1_horizons 010_trade_flow_1m 011_agent_outputs_daily \
         012_unknown_logic_version; do
  echo "=== $m ==="
  sudo -u agent docker compose exec -T postgres \
      psql -U agenttrade -d agenttrade -v ON_ERROR_STOP=1 \
      < db/migrations/${m}.sql || break
done
```

| Миграция | Что делает | Откат |
|---|---|---|
| `009_stage_8_1_horizons` | `horizon_h` в оценках, ключ `(signal_id, horizon_h)`, таблица `logic_version_windows` | `009_..._rollback.sql` — удаляет оценки 12ч и 24ч |
| `010_trade_flow_1m` | поминутные итоги ленты сделок | `010_..._rollback.sql` |
| `011_agent_outputs_daily` | суточные итоги выводов агентов | `011_..._rollback.sql` |
| `012_unknown_logic_version` | признак «версия неизвестна», правка уже записанных строк, индекс по времени журнала | `012_..._rollback.sql` |

Все четыре идемпотентны: повторное применение ничего не меняет. Миграция 009
останавливается сама, если у сигнала окажется две оценки на один горизонт, и
называет `signal_id` — удалять данные она не имеет права.

**Миграция 012 обязательна ДО следующего запуска ежесуточной задачи** — она
исправляет 42 строки, уже записанные с ложной версией (§15). Часть работы она
делает не сама: сутки, на которые пришлась первая известная граница, она
удаляет, а пересчитывает их ближайшая свёртка. Поэтому сразу после миграции
следует прогнать свёртку вручную, не дожидаясь 03:40 UTC:

```bash
cd /opt/agent-trade && sudo -u agent python3 scripts/retention.py
```

Ожидаемый вывод содержит строку вида «Выводов раньше самой ранней записанной
границы версий: 33895; строк итогов с признаком «версия неизвестна»
(logic_version = 0): N». Это норма, а не сбой.

**Миграции 010 и 011 обязаны быть применены ДО первого запуска ежесуточной
задачи по новым срокам.** Если таблиц итогов нет, задача остановит удаление
сырья сама (свёртка не выполнится) — но проверять это на своих данных не стоит.

### Шаг 5. Пересборка и запуск

Пересборка ОБЯЗАТЕЛЬНО с `--no-cache` (правило после дефекта D-9):

```bash
cd /opt/agent-trade
sudo -u agent docker compose build --no-cache
sudo -u agent docker compose up -d
```

В `docker-compose.yml` появился `shm_size: 512mb` у контейнера `postgres`
(§16), поэтому `up -d` ПЕРЕСОЗДАСТ контейнер базы. Данные лежат в томе
`pg_data` и переживают пересоздание; перерыв — несколько секунд. Проверить,
что настройка применилась:

```bash
sudo -u agent docker compose exec -T postgres df -h /dev/shm
```

## 14. Ограничения, действующие независимо от результата

1. **Критерии §11.2 и §11.3 не закрыты.** Двухчасовые прогоны на сервере
   обязательны и ничем здесь не заменяются: замеры этого отчёта длились
   35 минут, шли против заменителя биржи и на чужом железе (§0.3). Ни одно
   измеренное число не относится к Hetzner CX23.
2. **Пять токенов не дают пятикратного роста статистической мощности.**
   Криптовалюты сильно коррелированы; фактическая корреляция исходов считается
   ежесуточно и выводится в выгрузке (§7). Эффективное число независимых
   наблюдений меньше формального — насколько именно, покажут данные.
3. **Данные версий 4 и 5 не смешиваются.** Статистика версии 4 к версии 5
   неприменима: изменился и состав инструментов, и набор горизонтов. Окно
   наблюдений для версии 5 начинается с момента границы (§6).
4. **Горизонты 12ч и 24ч наберут выборку позже остальных.** Первые сутки после
   развёртывания оценок на 24 часах не будет вовсе — это не сбой.
5. **Логика принятия решения не менялась.** Этап расширяет охват: те же агенты,
   те же пороги, те же веса, тот же `MIN_AGENTS`. Ни один параметр агентов не
   тронут (§12 ТЗ).
6. **`MARKET_CLOSED_BARS_ONLY` остаётся false.** Эффект незавершённого бара
   измеряется отдельным этапом; сейчас переключатель только введён.
7. **Объём БД упирается в `trades`** — таблицу, которую сегодня не читает ни
   один агент. См. §4.3: решение о сроке её хранения за заказчиком, и принять
   его нужно ДО включения пяти токенов.
8. **Падение биржи в момент старта контейнера коллектора перезапускает
   контейнер, а не переживается внутри.** `src/collectors/runner.py:41`
   вызывает `exchange.load_markets()` без повторных попыток: если биржа
   недоступна именно в секунду старта, процесс падает с
   `ExchangeNotAvailable`, и подъём обеспечивает только политика
   `restart: unless-stopped` в `docker-compose.yml`. Наблюдалось на стенде
   22.08.2026: заменитель биржи выключился при перезапуске `dockerd`,
   коллектор набрал 20 перезапусков и поднялся сам, как только заменитель
   вернулся, — данные не потерялись, разделение рынков сохранилось
   (свечи только по споту, funding только по контракту). Это не дефект
   Этапа 8.1 — поведение унаследовано и одинаково во всех версиях, — но на
   сервере оно означает: короткая недоступность OKX на старте видна в
   `docker ps` как `Restarting`, и это нормальное самовосстановление.
   Тревожным признаком является только НЕубывающий счётчик перезапусков
   (`docker inspect --format '{{.RestartCount}}' <контейнер>`) при живой
   бирже. Внутрицикловые ошибки запросов таким свойством не обладают:
   их коллекторы переживают без падения процесса.

## 15. Дефект суточной свёртки: ложная версия логики (найден на сервере 22.08.2026)

### 15.1 Что произошло

Первый запуск ежесуточной задачи на сервере 22.08.2026 23:06 UTC напечатал:

```
ВНИМАНИЕ: выводов раньше самого раннего известного окна версий: 33895.
Им проставлена минимальная известная версия.
```

Результат в вечной таблице:

| logic_version | суток | выводов | min day | max day |
|---|---|---|---|---|
| 4 | 42 | 56 851 | 2026-08-08 | 2026-08-21 |

`logic_version_windows` при этом знает всего две границы: версия 4 с 16.08
16:25 UTC и версия 5 с 22.08 22:59 UTC. Выводы за 08.08–16.08 сделаны
версиями 1-3, а записаны как версия 4.

### 15.2 Почему это не мелочь

`agent_outputs_daily` не удаляется НИКОГДА, а сырьё `agent_outputs` живёт
90 суток. После удаления сырья проверить утверждение стало бы нечем, и в
проекте навсегда осталось бы: «данные версий 1-3 — это версия 4». Подстановка
ближайшей известной версии — то же самое, что подстановка суррогатных данных:
она создаёт правдоподобную, но ложную запись вместо честного «неизвестно» и
прямо нарушает основное правило проекта — версии логики не смешиваются.

Ошибка моя: восстановление версии по окнам я сделал с `coalesce(..., min
известной версии)`. Значение по умолчанию выглядело безобидной подстраховкой
от `NULL` в колонке `NOT NULL`, а на деле было утверждением о данных, которого
никто не проверял.

### 15.3 Признак «версия неизвестна»

Введено `logic_version = 0` (константа `UNKNOWN_LOGIC_VERSION` в
`scripts/retention.py`). Выводы раньше самой ранней ЗАПИСАННОЙ границы
получают его; ближайшая версия не подставляется.

Почему ноль, а не отдельная колонка-признак:

1. **Отличимость обеспечена кодом, а не соглашением.** Миграция 012 вешает на
   `logic_version_windows` ограничение `CHECK (logic_version > 0)`. Реальной
   версии 0 не существует и появиться не может — попытка отклоняется базой:
   ```
   ERROR: new row for relation "logic_version_windows" violates check
   constraint "logic_version_windows_version_positive"
   DETAIL: Failing row contains (0, 2026-08-22 23:22:44.661796+00, null).
   ```
2. **Молчаливое смешивание исключено по умолчанию.** Любой существующий отбор
   `WHERE logic_version = 4` строки с неизвестной версией НЕ ЗАХВАТИТ.
   Отдельная колонка-признак вела бы себя ровно наоборот: тот же отбор молча
   включал бы чужие данные у каждого, кто про новую колонку не знает.
3. **Разделение суток даётся даром.** `logic_version` уже входит в первичный
   ключ, поэтому сутки «неизвестно → версия 4» разделяются на две строки тем
   же механизмом, что и любая другая граница версий, без правок схемы.
4. **Переживает удаление сырья.** Признак лежит в самой вечной таблице.

### 15.4 Симметричный случай проверен: «позже последней границы» — не дефект

Вывод ПОЗЖЕ последней известной границы получает последнюю версию, и это
верно: у последнего окна нет конца (`ended_at IS NULL`), оно действует до
следующей границы. Версия здесь ИЗВЕСТНА — та, что работает сейчас. Незнание
было только «слева», до первой записанной границы.

Тест `test_outputs_after_the_last_known_window_get_the_last_version` проходит
и на коде ДО исправления, и после — поведение не менялось и меняться не
должно было.

### 15.5 Исправление уже записанного (миграция 012)

Работа разделена по тому, что можно установить точно:

* **Сутки целиком раньше первой границы** — `UPDATE ... SET logic_version = 0`.
  Сырьё не требуется: вся строка относится к неизвестному периоду целиком.
* **Сутки, слитые через границу** — строки удаляются, а пересчитывает их
  ежесуточная свёртка. Второй реализации расчёта в проекте нет и быть не
  должно, поэтому миграция ничего не считает сама: свёртка научена начинать
  счёт с самых ранних суток, по которым сырьё есть, а итогов нет.

  Датой такие сутки не выявляются: строка лежит не раньше начала своей версии,
  а ВНУТРИ неё. Признак другой — среди выводов строки есть сделанные раньше
  начала этой версии, а отдельной строки на раннюю часть суток нет. Условие
  «нет строки с меньшей версией по той же группе» и делает шаг идемпотентным.
* **Сутки без сырья** — НЕ ТРОГАЮТСЯ. Миграция печатает `WARNING` с числом
  таких строк: удалить их значило бы потерять данные безвозвратно, а
  разделить по версиям уже нечем. Решение по ним принимает человек.

## 16. VACUUM на больших таблицах: разделяемая память контейнера

### 16.1 Что произошло

После удаления 3.57 млн строк `trades` на сервере штатный `VACUUM ANALYZE`
упал:

```
ERROR: could not resize shared memory segment to 67145248 bytes:
No space left on device
```

Речь не о диске: параллельная чистка индексов раскладывает список мёртвых
строк в РАЗДЕЛЯЕМОЙ памяти, а docker даёт контейнеру `/dev/shm` 64 МБ по
умолчанию. Ежесуточная задача завершилась с ошибкой на штатной операции —
при ежедневном запуске это ложная тревога каждую ночь.

### 16.2 Решение: оба, и по разным причинам

**Основное — `PARALLEL 0` в `scripts/retention.py`.** Чистка после удаления
идёт как `VACUUM (ANALYZE, PARALLEL 0)`. Это снимает зависимость от размера
`/dev/shm` полностью: параллельные рабочие процессы не запускаются, разделяемая
память не нужна вовсе. Выбрано основным потому, что скрипт обязан работать и
там, где настройку окружения не применили, — код не имеет права полагаться на
чужую конфигурацию. Цена: чистка идёт в один поток. Для ночной задачи в
03:40 UTC это не имеет значения — ручной прогон с `PARALLEL 0` на сервере
занял минуту.

**Дополнительно — `shm_size: 512mb` у контейнера `postgres`.** Одним
`PARALLEL 0` проблема не закрывается: тот же предел ждёт любую параллельную
операцию, а `count(*)` по `trades` есть и в суточной сводке, и в `/summary`
бота, и в `scripts/measure_load.sh`. Обойти его выбором плана нельзя.
`/dev/shm` — это tmpfs: память расходуется только по факту использования, и
поднятый предел ничего не стоит, пока не нужен.

Применение требует пересоздания контейнера базы (`docker compose up -d`).
Данные лежат в томе `pg_data` и переживают его; перерыв — несколько секунд.
Если пересоздание сейчас нежелательно, шаг можно отложить: ежесуточная задача
работает и при 64 МБ.

Проверено на стенде: `VACUUM (ANALYZE, PARALLEL 0) trades;` проходит без
ошибки.
