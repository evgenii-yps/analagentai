## Итог одним абзацем, без технических терминов

Раньше у нас были только результаты самой системы, и сравнить их было не с чем.
Продажи выглядели прибыльными — но эти двое суток рынок просто падал, а когда
рынок падает, выигрывает кто угодно, кто продаёт, даже если решение принимала
подброшенная монета. Теперь рядом с результатами системы считаются результаты
пяти заведомо бессмысленных правил: «покупать всегда», «продавать всегда»,
«бросать монету», и отдельно — «входить каждый час просто по часам, не глядя на
систему». Все они считаются на тех же самых моментах, по тем же ценам и по той
же мерке. Появилась линейка: теперь видно не только сколько система заработала,
но и заработала ли бы столько же обезьяна. Вдобавок к каждому сравнению
считается честная оговорка: если данных мало, чтобы отличить систему от монеты,
так прямо и написано — «различить нельзя, выборки не хватает». **Ничего в работе
системы не изменилось: она принимает те же решения и шлёт те же уведомления.**
Выводов о том, хороша система или плоха, этот этап не делает и делать не может —
за двое суток одного падающего рынка такой вывод был бы преждевременным.

## §3. Предпроверка — **блокирующего нет**

### 1. Хранит ли `risk_targets` историю по датам? — **ДА, ИСТОРИЮ**

Ответ даёт первичный ключ, и он одинаков на стенде и на сервере (миграция 014
применена там и там) — **[стенд]**, но это утверждение о схеме, а не о данных:

```
risk_targets_pkey | PRIMARY KEY (instrument_id, horizon_h, direction, computed_at)
```

`computed_at` **входит в ключ**, а запись идёт чистым `INSERT` — каждый суточный
пересчёт добавляет новую строку и не трогает прежние. Блокирующее условие §3
(«только текущий срез») **не выполнено**, работа продолжена правомерно.

Дополнительно раздел 1b скрипта отвечает на вопрос, которого схема не решает:
**хватает ли этой истории на даты сигналов**. Он печатает `covered`/`uncovered`
по каждому горизонту. Пары без исторической цели пропускаются и считаются
отдельно (`skipped_no_target`); подставлять им сегодняшнюю цель код не может
конструктивно — запрос содержит `computed_at <= момента входа`.

### 2. Хранит ли `signal_targets` цель для обоих направлений? — **НЕТ, ТОЛЬКО ДЛЯ СВОЕГО**

```
signal_targets_pkey | PRIMARY KEY (signal_id, horizon_h)
max_directions_per_pair = 1
```

Одна строка на пару (сигнал, горизонт), направление — колонка. Значит, для
встречного направления замороженной цели **не существует**, и она обязана
браться из `risk_targets` за дату входа. Это и определило устройство §4.

## §4–§5. Шесть стратегий: что именно реализовано

Чистый модуль `src/baseline/strategies.py` (ни базы, ни сети, ни «сейчас»).

**Монета детерминирована** — направление вычисляется как
`sha256(seed:signal_id:horizon_h)`, а не берётся из `random`. Разница
принципиальная: `random.seed(...)` даёт воспроизводимую *последовательность*, но
не воспроизводимое *соответствие* — достаточно вставить один сигнал в середину
выборки, и вся монета ляжет заново на другие сигналы, а прежние числа отчёта
перестанут воспроизводиться молча. Здесь направление привязано к самой тройке,
поэтому не зависит ни от порядка обхода, ни от состава выборки. `sha256` взят
вместо встроенного `hash()` намеренно: `hash()` для строк рандомизируется от
запуска к запуску.

**Откуда берётся цель** — и почему по-разному:

| Случай | Источник | `target_source` |
|---|---|---|
| направление стратегии совпало с направлением сигнала | замороженная цель `signal_targets` | `frozen` |
| направление встречное | историческая строка `risk_targets` за дату входа | `risk_targets:<дата>` |
| сетка §5 (сигнала нет вовсе) | историческая строка `risk_targets` | `risk_targets:<дата>` |

Различение обязательно, и вот почему. Возьми мы историческую цель везде,
`always_buy` расходился бы с `system` на сигналах «покупать» — при одинаковом
направлении, одинаковой цене и одинаковом окне, **только** из-за разного
источника цели. Сравнение показало бы разницу там, где её нет.

**Проверено фактом [стенд]:** на 30 сигналах «покупать» строки `always_buy` и
`system` совпали по направлению, цели, источнику, исходу и результату —
**30 из 30**.

## §6. Схема

Миграция `016_strategy_outcomes.sql` (номер свободен, конфликта нет).
Первичный ключ — `(strategy, instrument_id, entry_ts, horizon_h)`, а **не**
`(strategy, signal_id, horizon_h)`: у сетки §5 сигнала нет по построению, и ключ
обязан работать и для неё.

Сверх состава колонок из ТЗ добавлены только **ограничения** — база обязана
ловить ошибку раньше отчёта. Девять `CHECK`:

* перечни стратегий (шесть) и исходов (те же пять, что в 8.8) — закрыты;
* `target_source` — либо `frozen`, либо `risk_targets:` с датой по маске;
* согласованность формы строки (у `ambiguous`/`no_data` нет ни момента касания,
  ни результата);
* **сетка не может быть привязана к сигналу**, а стратегии §4 — обязаны;
* **зерно есть тогда и только тогда, когда была случайность** (`coin_flip`).

Таблица внесена в `PROTECTED_TABLES`. Откат — `016_strategy_outcomes_rollback.sql`.

**Проверено [стенд]:** применение → повторное применение → откат → повторное
применение, без ошибок; 12 ограничений (9 `CHECK` + первичный и два внешних
ключа). Та же последовательность выполняется тестом на живой базе.

## §7. Где считается и сколько это стоит

Нового сервиса **не заведено** — тот же `barrier` профиля `tools`, другая
команда. Расписание **04:25 UTC**, после исходов системы в 04:10: моменты входа
берутся из их таблицы, и запуск раньше строил бы линейку на вчерашнем наборе
сигналов.

### Ключевое решение: одно окно свечей на все стратегии

Четыре стратегии §4 на одном моменте смотрят на **один и тот же** отрезок
свечей: он зависит от инструмента, момента и горизонта, но не от того, покупаем
мы или продаём. Читать его четырежды значило бы учетверить самую дорогую часть
работы ради одного и того же ответа. Расчёт читает окно один раз.

**Замер [стенд]** — три полных пересчёта с нуля:

```
seconds=0.510  windows_read=124  written=368
seconds=0.471  windows_read=124  written=368
seconds=0.492  windows_read=124  written=368
```

124 окна на 368 строк — то есть ровно одно окно на момент, а не шесть.
Это **≈ 253 окна в секунду** на стендовых окнах (горизонты 1 и 4 часа,
60 и 240 минутных баров).

**Повторный прогон [стенд]:** `written=0`, `windows_read=0`, `seconds=0.008`.
Идемпотентный запуск не читает ни одного окна: уже посчитанные ключи
вычитываются одним запросом заранее.

### Оценка для сервера — это АРИФМЕТИКА, а не замер

11 559 сигналов × 4 горизонта ≈ **46 236** окон, плюс сетка (окно наблюдения
≈ 49 часов × 5 инструментов × 4 горизонта ≈ 980) ≈ **47 200** окон. Средний
размер окна на сервере больше стендового примерно вчетверо (там есть горизонты
12 и 24 часа — 720 и 1440 баров против 60 и 240).

Прямая экстраполяция даёт **≈ 12 минут**, то есть под потолком §7 (20 минут), но
без большого запаса. **Это не замер и замером не является:** другое железо,
другой объём базы, другое состояние кэша. Поэтому шаг 4 runbook — прогон с
`--limit` на части выборки с засечкой времени, и только потом полный.

Раздел 8 `verify_8_9.sh` читает время последнего прогона из журнала и печатает
🟡 при превышении 1200 с, прямо называя требование ТЗ переписать чтение окон
пакетами.

## §8. Сравнение и честная оценка неопределённости

Два инструмента, и читать их надо **вместе**:

* `analysis/sql/09_baseline_compare.sql` — описательные числа: объём, доля
  `target`, средний результат, разбивки по направлению и по признаку
  «сигнал отправлен человеку», происхождение целей;
* `scripts/baseline_bootstrap.py` — **доверительный интервал разницы**.

### Почему одной таблицы средних недостаточно

Разница средних всегда чем-нибудь да отличается от нуля. На выборке в двое суток
она отличается от нуля даже тогда, когда никакой разницы нет: числа пляшут просто
потому, что сигналов мало. Строка «система лучше на 0.3%» без оценки этой пляски
создаёт уверенность, которой у данных нет, — и решения принимаются по шуму.

Метод — **парный** бутстрэп: 10 000 пересборок выборки с возвращением, интервал
95%. Пересобираются **пары целиком**, а не два ряда по отдельности: система и
базовая стратегия стоят на одних и тех же сигналах, и выбросить это совпадение
значило бы получить интервал шире настоящего — то есть объявить «различить
нельзя» там, где различить можно. Отдельным тестом проверено, что бутстрэп
именно парный: на данных с постоянной разницей он обязан дать интервал нулевой
ширины, и даёт.

Три формулировки — дословно те, что предписаны ТЗ, и других в коде нет
(проверяется тестом):

```
система лучше, интервал не пересекает ноль
система хуже, интервал не пересекает ноль
различить нельзя, выборки не хватает
```

**Пример вывода [стенд]** — на искусственной выборке, где ответ известен заранее:

```
 ВСЕ ГОРИЗОНТЫ ВМЕСТЕ
  система против always_buy     пар: 60  разница средних: +1.0000%  интервал 95%: [+0.7333; +1.2667]
                                → система лучше, интервал не пересекает ноль
  система против always_sell    пар: 60  разница средних: -1.0000%  интервал 95%: [-1.2667; -0.7333]
                                → система хуже, интервал не пересекает ноль
  система против coin_flip      пар: 60  разница средних: -0.0667%  интервал 95%: [-0.4333; +0.3000]
                                → различить нельзя, выборки не хватает
```

Все три формулировки работают. **Ни одно из этих чисел не относится к рынку** —
выборка построена так, чтобы падающий ряд давал `always_sell` победу, а
`always_buy` — проигрыш. Смысл примера только в том, что механизм считает.

### Краевой случай, который иначе прочли бы неверно

На сигналах «покупать» `always_buy` — это **та же самая сделка**, что у системы.
Разница там ровно ноль, интервал `[0; 0]`, и формулировка выпадает в «различить
нельзя, выборки не хватает» — что прочли бы как «данных мало», хотя данные здесь
идеальны. Формулировка оставлена предписанной, но рядом печатается причина:
`(стороны совпадают по построению: это одна и та же сделка)`.

### Что в сравнение НЕ входит, и это не упущение

* `grid_buy` и `grid_sell` — общих пар с системой у них нет по построению
  (они входят каждый час независимо от сигналов). Их числа печатает раздел 9.6
  запроса — **как соседство, а не как вычитаемое**;
* пары, где хоть одна сторона дала `ambiguous` или `no_data`: там неизвестно, что
  произошло, а разность с неизвестным не определена;
* группы меньше 20 пар: бутстрэп на трёх наблюдениях даёт интервал, но это
  интервал о трёх числах, а не о рынке. Печатается «различить нельзя» с прямым
  указанием причины.

## §9. Исправления, найденные при развёртывании 8.8

Все три выполнены в `deploy/verify_8_8.sh` и заложены в `verify_8_9.sh`.

**1. Печатался справочник всех мыслимых причин, включая заведомо ложные.**
Человек был вынужден сам угадывать, какая строка относится к делу. Теперь
итог печатает **только фактически сработавшее** — находки накапливаются в
массивы по мере обнаружения, и в конце выводятся ровно они.

**2. Классы блокирующего не различались.** Ненайденный файл расписания вёл к тому
же вердикту «откатить всё», что и нарушение границы этапа. Введены два класса:

```
🔴 БЛОКИРУЮЩЕЕ (откат):      нарушена граница этапа, одной командой не чинится
🔴 БЛОКИРУЮЩЕЕ (устранимо):  развёртывание неполно, запрещённого не произошло
   └ команда: <точная команда устранения>
```

Оба считаются блокирующими — различается **что делать**, а не серьёзность.
Проверено **[стенд]**: отсутствие cron даёт «устранимо» с командой и вердикт
«откат НЕ нужен», а не предложение откатывать развёртывание.

**3. Ожидание девяти колонок в `signal_evaluations` устарело.** Исправлено не
числом, а по существу: сверяются **имена обязательных колонок**, а не их
количество. Число колонок — плохой признак: оно меняется от любой правки схемы,
включая безобидную, и ничего не говорит о том, что именно изменилось. Настоящее
нарушение обещания «таблицы не изменяются» — это **исчезнувшая** колонка, и
теперь проверяется именно она; фактическое число печатается справкой.

> **Расхождение, которое стоит отметить.** На сервере в `signal_evaluations`
> десять колонок, на стенде — девять (`db/init.sql` + миграции 007–016 дают
> девять). Десятой колонки в репозитории нет. Проверка по именам к этому
> нечувствительна и работает в обоих случаях, но само расхождение означает, что
> схема сервера ушла от схемы репозитория. Разобраться с этим стоит отдельно —
> в рамках этого этапа я схему не трогал.

### Почему пункты 7 и 8 не выполнены — фактом

```
$ docker compose --profile "*" build --no-cache
target decision: failed to solve: python:3.12-slim: ... 429 Too Many Requests
$ docker compose up -d postgres
failed to copy: ... production.cloudfront.docker.com ... : Forbidden
```

Ограничение среды исполнителя, не дефект этапа. **Что сделано вместо, и чем это
не является:** конвейер прогнан штатной точкой входа `python -m src.baseline_main`
против настоящего PostgreSQL 16.13 с применённой схемой, на том же коде, что
уйдёт в образ. Это **не** доказательство работы в образе. Прогон в образе обязан
выполнить владелец (шаги 3–5 runbook) и **фактический вывод приложить к отчёту**.

## Что НЕ сделано и почему

1. **Прогон в собранном образе (§10.7, §10.8).** Сеть до Docker Hub закрыта
   политикой egress. Шаги 3–5 runbook.
2. **Числа [сервер] по объёму `signal_outcomes_barrier` (§3.4).** Нет доступа;
   скрипт готов, шаг 1 runbook.
3. **Замер времени на сервере (§7).** На стенде выборка в 600 раз меньше;
   перенос стендового числа был бы выдумкой. Шаг 4 runbook — с `--limit`.
4. **Выводов о качестве системы нет** — так требует §11 ТЗ, и это не формальность:
   выборка двое суток, один режим рынка.
5. **Десятая колонка `signal_evaluations` на сервере** не исследована — вне
   области этапа, отмечена в §9.

## Runbook для сервера

По одной команде на шаг, под пользователем `agent` из `/opt/agent-trade`.

**1. Предпроверка §3 (блокирующая; вывод приложить к отчёту).**
```bash
docker compose exec -T postgres psql -U agenttrade -d agenttrade -f /dev/stdin < scripts/precheck_8_9.sql
```

**2. Обновить код.**
```bash
git fetch origin && git checkout main && git pull --ff-only
```

**3. Применить миграцию.**
```bash
docker compose exec -T postgres psql -U agenttrade -d agenttrade < db/migrations/016_strategy_outcomes.sql
```

**4. Пересобрать образы.**
```bash
docker compose --profile "*" build --no-cache && docker compose up -d --remove-orphans
```
> На Compose v5 `--profile` — флаг **верхнего уровня**; `build --profile "*"`
> отвечает `unknown flag` (проверено **[стенд]**, v5.1.1).

**5. ЗАМЕР на части выборки — до полного прогона (вывод приложить).**
```bash
time docker compose --profile tools run --rm --no-deps barrier python -m src.baseline_main --limit 500
```

**6. Полный расчёт линейки (вывод приложить).**
```bash
docker compose --profile tools run --rm --no-deps barrier python -m src.baseline_main
```

**7. Проверка развёртывания.**
```bash
sudo -u agent bash /opt/agent-trade/deploy/verify_8_9.sh
```

**8. Описательные числа §8 (вывод приложить).**
```bash
docker compose exec -T postgres psql -U agenttrade -d agenttrade -f /dev/stdin < analysis/sql/09_baseline_compare.sql
```

**9. Доверительные интервалы §8 — читать вместе с шагом 8 (вывод приложить).**
```bash
docker compose --profile tools run --rm --no-deps barrier python -m scripts.baseline_bootstrap
```

**10. Поставить регламент 04:25 UTC.**
```bash
sudo cp deploy/agent-trade-baseline.cron /etc/cron.d/agent-trade-baseline && sudo chmod 644 /etc/cron.d/agent-trade-baseline
```

### Откат этапа (данные системы не затрагиваются)

docker compose exec -T postgres pg_dump -U agenttrade -d agenttrade -t strategy_outcomes > /tmp/strategy_outcomes_backup.sql
