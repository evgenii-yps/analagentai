## 3. Расчёт согласованности — и почему НЕ через парсинг rationale

Согласованность пересчитывается из `agents_payload` **той же формулой**, что и
Decision Agent (`src/decision/agent.py`):

```python
directions = [SIGNAL_VALUE[o["signal"]] for o in fresh]   # bullish=+1, bearish=-1, neutral=0
pos = sum(1 for d in directions if d > 0)
neg = sum(1 for d in directions if d < 0)
agreement = abs(pos - neg) / len(fresh)
```

Единая реализация — `src.notify.agent.compute_agreement()`. Её вызывают **и**
форматтер сигнала (`format_signal_message`), **и** бот (`handlers.render_signal_card`)
— чтобы формула жила в одном месте.

**Почему не парсинг rationale.** Поле `rationale` — свободный текст
(`market=bullish(0.70), …; балл=+0.42, согласованность=0.67 → buy`), его формат
может измениться в любом следующем этапе. Регулярка по нему — хрупкая связь
между «как записали строку» и «как её читают». `agents_payload` — структурный
JSON (`{agent, signal, confidence, ts}`), это стабильный контракт. Пересчёт по
нему — чистое чтение, логику решений не затрагивает.

Словесная расшифровка: `≥0.9` — «агенты единодушны»; `0.5–0.9` — «агенты скорее
согласны»; `<0.5` — «мнения расходятся».

Подтверждено тестами: `tests/test_bot.py::test_agreement_*` (единодушие,
смешанное, противоположное, из JSON-строки, пусто→None) и
`tests/test_notify.py::test_format_message_agreement_*` (все три градации).

## 4. Как решён вопрос с /summary

`src/health/daily_report.py` — host-скрипт на стандартной библиотеке, работает по
cron в 06:00 UTC. Его логику трогать нельзя (сторонний импорт сломал бы рабочую
сводку). Из контейнера он недоступен.

**Решение.** `/summary` считает свои метрики **самостоятельно по БД и Redis**
(отдельная реализация в `src/bot/queries.py`, дублирование запросов осознанное):

| Метрика | В /summary |
|---|---|
| Heartbeat всех сервисов | считается заново (Redis GET по 11 ключам) |
| Приток данных за 24 ч (6 таблиц) | считается заново (`data_counts_24h`) |
| Сигналы за 24 ч: раскладка, отправлено, поглощено, кандидаты, закрыто | считается заново (`signal_counts_24h`) |
| Размер БД | считается заново (`pg_size_pretty(pg_database_size(...))`) |
| Аптайм, диск, память, статусы контейнеров | **заглушка**: «доступно только в суточной сводке в 06:00 UTC» |

Хостовые метрики требуют доступа к Docker и хосту, которого у контейнера-бота нет
(и не должно быть — §3.4), поэтому они заменены строкой-заглушкой.

## 7. Фактическое потребление ресурсов (docker stats)

**Проверяется при развёртывании.** В среде разработки нет запущенного стека,
поэтому реальные цифры снимаются на сервере после подъёма:

```bash
sudo -u agent docker -C /opt/agent-trade stats --no-stream agent-trade-bot-1
# или:
cd /opt/agent-trade && sudo -u agent docker compose stats --no-stream bot
```

Ожидание — `<50 МБ RAM` (лёгкий async-сервис: httpx + один RO-пул asyncpg 1..5
соединений, без pandas/ccxt в горячем пути). На CX23 (4 ГБ, свободно ~2.8 ГБ)
запас достаточный. Фактическое значение впишите сюда после подъёма.

## 8. Что делает заказчик — развёртывание на действующий сервер

> Заказчик не программист. Все шаги — по порядку, копируются целиком. Git-команды
> на сервере — с префиксом `sudo -u agent git -C /opt/agent-trade` (иначе ошибка
> «dubious ownership»). Репозиторий клонирован с `--depth 1 --branch`, поэтому
> перед сменой ветки нужны `git remote set-branches` и `git fetch`.

**Шаг 0. Зайти на сервер и перейти в каталог приложения.**
```bash
ssh agent@46.224.52.105
cd /opt/agent-trade
```

**Шаг 1. Бэкап БД (обязательно перед изменениями).**
```bash
sudo -u agent /opt/agent-trade/scripts/backup_db.sh
ls -lt /opt/agent-trade/backups | head -3    # убедиться, что появился свежий .dump.gz
```

**Шаг 2. Сохранить копию текущего .env (там пароли — не потерять).**
```bash
sudo cp /opt/agent-trade/.env /opt/agent-trade/.env.backup-$(date +%F)
```

**Шаг 3. Переключиться на рабочую ветку (после влития — на `main`).**
```bash
sudo -u agent git -C /opt/agent-trade remote set-branches origin '*'
sudo -u agent git -C /opt/agent-trade fetch --depth 1 origin main
sudo -u agent git -C /opt/agent-trade checkout -B main origin/main
sudo -u agent git -C /opt/agent-trade log --oneline -1     # проверить, что это нужный коммит
```
> До влития ветки в `main` вместо `main` подставьте
> `claude/telegram-bot-signal-readability-y4d9tq` в обеих командах (fetch и checkout).

**Шаг 4. Добавить новые ключи в .env (роль ro и настройки бота).**
Установщик умеет дописывать недостающие ключи, не затирая заполненные. Проще
всего — прогнать его повторно (идемпотентен), но если хочется без него, добавьте
вручную сгенерированный пароль роли только на чтение:
```bash
# Сгенерировать пароль роли ro (32 символа) и дописать блок бота, если его нет:
grep -q '^POSTGRES_RO_PASSWORD=' /opt/agent-trade/.env || \
  echo "POSTGRES_RO_PASSWORD=$(tr -dc 'A-Za-z0-9' </dev/urandom | head -c 32)" | sudo tee -a /opt/agent-trade/.env
grep -q '^BOT_ENABLED=' /opt/agent-trade/.env || printf 'BOT_ENABLED=true\nBOT_POLL_TIMEOUT=30\nBOT_ALLOWED_CHAT_IDS=\nBOT_MAX_ROWS=20\nBOT_RATE_LIMIT_SEC=3\n' | sudo tee -a /opt/agent-trade/.env
sudo chmod 600 /opt/agent-trade/.env
```
`BOT_ALLOWED_CHAT_IDS` можно оставить пустым — тогда бот отвечает только вашему
`TELEGRAM_CHAT_ID` (1462906955). Роль `agenttrade_ro` в БД создаётся сервисом
бота автоматически при первом старте.

## 9. Что пошло не так и как обошли

1. **Нет доступа к продакшн-серверу и живой БД из среды разработки.** Обойдено:
   вся логика форматирования вынесена в чистые функции и прогнана на
   представительных данных (примеры в §2/§6), а пункты, требующие живой
   БД/хоста, снабжены точными командами проверки для заказчика (§8) и честно
   помечены «проверяется при развёртывании» (§5).

2. **`asyncpg` не поддерживает psql-подстановку `:'ro_password'` из ТЗ §8.**
   DO-блок с `:'ro_password'` — синтаксис `psql`, а не драйвера. Обошли:
   пароль подставляется на стороне PostgreSQL через `format(..., %L)`
   (`quote_literal`) — без ручной сборки строки и риска инъекции. Роль
   создаётся/обновляется идемпотентно (CREATE если нет, иначе ALTER — чтобы
   вход роли работал даже после ротации пароля).

3. **Порядок старта: бот может подняться раньше, чем готова БД.** `depends_on:
   [postgres, redis]` без `condition: service_healthy` (как у `export`). Обошли:
   подготовка роли ro и RO-пула повторяется с паузой 15 с, пока БД не станет
   доступна; при этом бот **никогда** не ходит запросами под основным
   пользователем (ТЗ §8) — основное соединение используется лишь для одноразового
   создания роли.

4. **Формат логирования у остальных сервисов в compose не задан явно.** ТЗ §10
   требует json-file `max-size:10m`/`max-file:3` «как у остальных». В
   `docker-compose.yml` у прочих сервисов блока `logging` нет (действует
   умолчание демона). Для `bot` добавили блок `logging` явно — это буквально
   выполняет требование ТЗ и не меняет поведение прочих сервисов.

5. **`agents_payload` из asyncpg приходит строкой (JSONB без кодека).** Обошли:
   `normalize_payload` принимает и список, и JSON-строку, и None — согласованность
   и разбор агентов считаются одинаково в обоих случаях (тест
   `test_agreement_from_json_string`).

6. **Блок 4 /stats — условная строка, а DoD требует «пять блоков».** Обошли:
   блок 4 всегда выводится с заголовком; содержимое условное (при `n<30` —
   предупреждение, иначе нейтральная строка «наблюдений ≥ 30»). Суждений
   «система работает хорошо/плохо» бот не выдаёт.

## Предложения, зафиксированные и НЕ реализованные (ТЗ §7.6)

По ходу работы напрашивались команды, меняющие состояние (`/restart`,
`/setthreshold`, `/enable`, `/disable`, вкл/выкл сервисов). **Ни одна не
добавлена** — бот строго только на чтение. Фиксируем как предложение на будущее,
если заказчик осознанно захочет управляющий контур (тогда — отдельный этап с
явной моделью доступа и аудитом).
