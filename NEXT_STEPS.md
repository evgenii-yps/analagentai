## Общая оговорка по выборке (важно для обеих SQL-проверок)

Все запросы ниже привязаны к **фиксированной нижней границе = момент выката
Этапа 7.0**, а не к скользящему окну `now() - N days`. Скользящее окно при запуске
позже намеченного срока начало бы смешивать разные периоды и «съезжать» с границы
режимов — выборка стала бы невоспроизводимой.

Границу задаём одним из двух способов (эквивалентны):

- **A. Явной датой выката.** Подставьте дату выполнения Шага 5 §7 отчёта 7.0
  («Граница режимов», §8 отчёта — там она фиксируется при развёртывании):
  ```
  ts >= 'ГГГГ-ММ-ДД'::timestamptz     -- дата выката Этапа 7.0
  ```
- **B. Выводом границы из данных (если дату не записали).** Поле
  `confidence_raw` в `agent_outputs.metrics` существует ТОЛЬКО в коде версии 2,
  поэтому первый вывод с этим полем = момент выката:
  ```
  ts >= (SELECT min(ts) FROM agent_outputs WHERE metrics ? 'confidence_raw')
  ```

Ниже в запросах используется вариант B (не требует ручной даты и самодокументирован).
Для строго воспроизводимого «замороженного» снимка добавьте ещё и фиксированную
**верхнюю** границу `AND ts < 'ГГГГ-ММ-ДД'::timestamptz` (дата анализа).

## 1. Проверка констант нормировки уверенности (Задача A Этапа 7.0)

**Контекст.** Нормировка опирается на `CONFIDENCE_SCALE = 0.15` (liquidity) и
`0.10` (futures) — эмпирические максимумы сырой уверенности из трёхсуточного
наблюдения в ОДНОМ рыночном режиме (market = `1.0`, тождество). Это делает
калибровку чувствительной к смене режима: при росте волатильности стакана
liquidity упрётся в потолок `1.0`, при затухании — снова провалится. `confidence_raw`
сохранён в `metrics` именно для этой проверки на новых данных.

### Запрос 1 — эмпирические перцентили/максимум `confidence_raw` против констант
```
docker compose exec -T postgres psql -U agenttrade -d agenttrade -c "SELECT agent, count(*) n, round(max((metrics->>'confidence_raw')::float)::numeric,4) max_raw, round((percentile_cont(0.99) WITHIN GROUP (ORDER BY (metrics->>'confidence_raw')::float))::numeric,4) p99_raw, round((percentile_cont(0.95) WITHIN GROUP (ORDER BY (metrics->>'confidence_raw')::float))::numeric,4) p95_raw, round((percentile_cont(0.50) WITHIN GROUP (ORDER BY (metrics->>'confidence_raw')::float))::numeric,4) median_raw FROM agent_outputs WHERE metrics ? 'confidence_raw' AND signal IN ('bullish','bearish','neutral') AND ts >= (SELECT min(ts) FROM agent_outputs WHERE metrics ? 'confidence_raw') GROUP BY agent ORDER BY agent;"
```
**Как читать.** Сравнить `p99_raw` с константой `CONFIDENCE_SCALE` (liquidity `0.15`,
futures `0.10`). `p99` устойчивее `max` к выбросам и является кандидатом в новый
масштаб. `p99_raw` заметно **выше** константы → режим стал волатильнее, нормировка
упирается в потолок; заметно **ниже** → уверенность хронически проваливается.

### Запрос 2 — прямой замер «упирания в потолок» (доля насыщений на 1.0)
```
docker compose exec -T postgres psql -U agenttrade -d agenttrade -c "SELECT agent, count(*) n, round(100.0*avg((confidence>=1.0)::int),2) pct_clipped, round((percentile_cont(0.5) WITHIN GROUP (ORDER BY confidence))::numeric,3) median_norm FROM agent_outputs WHERE metrics ? 'confidence_raw' AND signal IN ('bullish','bearish','neutral') AND ts >= (SELECT min(ts) FROM agent_outputs WHERE metrics ? 'confidence_raw') GROUP BY agent ORDER BY agent;"
```
**Как читать.** Высокий `pct_clipped` у liquidity/futures → масштаб мал (волатильность
выросла); `pct_clipped ≈ 0` при низком `median_norm` → масштаб велик (затухание).

**Критерий существенного расхождения** (ориентир): `p99_raw` отличается от
константы более чем на ~±50%, ИЛИ `pct_clipped > ~5%`. Ниже — калибровка признаётся
годной, константы не трогаем.

### Если расхождение существенно
Варианты (из ТЗ 7.0 §3.2), в порядке возрастания сложности:
1. **Обновить константы** до новых `p99_raw` (тот же бесстатусный вариант 1, но
   перекалиброванный). Дёшево, детерминированно; но снова «снимок одного режима».
2. **Вариант 2 — калибровка по историческому распределению** (перцентиль сырой
   уверенности как масштаб). Сопоставимость гарантирована; требует хранить и
   обновлять референсное распределение.
3. **Вариант 3 — ранговое преобразование** в скользящем окне. Устойчиво к выбросам;
   теряется абсолютная величина, нужен размер окна.
4. **Адаптивный масштаб** со скользящим окном собственных выводов агента.

### Риск адаптивного масштаба (взвесить отдельно)
Адаптивный масштаб (варианты 2–4) вводит **состояние** и делает `confidence`
зависимой от истории — страдают воспроизводимость и детерминизм (ровно та причина,
по которой на Этапе 7.0 выбран бесстатусный вариант 1). Взвесить это против
устойчивости к смене режима. Требования к состоянию, если пойдём этим путём:
хранить явно (БД/Redis), восстанавливать после перезапуска, отсутствие состояния
→ разумное поведение по умолчанию (как в §3.2 ТЗ 7.0). Правка меняет `score`/
`probability` → обнуляет статистику → новый инкремент `LOGIC_VERSION` (до 3).

## 2. Инерция funding (Задача C.3 Этапа 7.0)

**Контекст.** funding обновляется ~3 раза в сутки (расчёт каждые 8 ч), а Futures
Agent работает раз в минуту → ~480 циклов подряд видит одно и то же значение
funding. Составляющая сигнала от funding — кусочно-постоянная ступенька,
переизлучаемая 1440 раз в сутки.

**Предложение.** Понижать вклад funding, когда его `ts` не менялся (опираться на
open interest, обновляемый каждые 60 c), либо пересчитывать funding-составляющую
только при новом `ts` funding.

**Почему отложено.** Любое из решений меняет направление сигнала непредсказуемым
образом (по §5.2.3 ТЗ 7.0 такое выносится в следующий этап). На Этапе 7.0 инерция
направление не искажает — только «переизлучает» его. Реализовывать только если
решение не меняет направление непредсказуемо; иначе — снова отдельный этап с
инкрементом `LOGIC_VERSION`.

## Порядок и предостережение

1. Дождаться ~3 недель данных на `logic_version=2`.
2. Прогнать запросы 1–2, зафиксировать `p99_raw`/`pct_clipped`.
3. Принять решение по константам (оставить / перекалибровать / адаптив) с оценкой
   риска состояния.
4. Отдельно — решение по инерции funding.

**Нельзя смешивать версии логики при анализе.** Все ручные SQL по сигналам —
только `WHERE logic_version = 2`; бот `/stats` это делает автоматически. Любая
правка из этого файла, меняющая `score`/`probability`/направление, требует нового
инкремента `LOGIC_VERSION` и заново обнуляет окно наблюдения.
