# Версия логики 7 — отчёт исполнителя

Снятие слотов, антиспам по токену, уведомления только по сделкам.
ТЗ «Версия логики 7», разделы §1–§10.

---

## 1. Что сделано одной фразой

Система перестала ограничивать **число** одновременных сделок и начала
ограничивать их **частоту**; в Telegram уходят только события сделок.
`LOGIC_VERSION` 6 → 7. Данные версии 6 не тронуты ни одной строкой.

---

## 2. Что проверено в коде ДО правок (а не взято из ТЗ на веру)

ТЗ §2 называет факты, на которых построен состав работ. Исполнитель проверил
каждый из них по коду — и нашёл один, который в ТЗ назван не полностью.

| Утверждение ТЗ | Проверено | Где |
|---|---|---|
| Служба позиций читает сигналы напрямую: порог 0.8, полный кворум, только покупки | верно | `db.get_position_candidates` |
| Антиспам уведомлений к сделкам не применяется | верно | `should_open` не смотрит на `notified` |
| Ограничителей два: слоты и «один инструмент — одна позиция» | верно | `should_open`: `slots_full`, `instrument_busy` |
| Правило выхода: 48 ч, ожидание плюса с 24 ч, предела нет | верно | `check_exit_plus_wait`, миграция 025 |

**Найденное сверх ТЗ, и это определило состав работ по базе.** Правило «один
инструмент — одна позиция» закреплено **не только кодом**: его записывает
частичный уникальный индекс `ux_positions_one_open_per_instrument` (миграция
018). Сними правило одним лишь кодом — и вторая позиция по токену получила бы
отказ вставки, служба сочла бы его штатной гонкой (`positions_race_skipped=1`),
и сделок не прибавилось бы **ни одной** при совершенно честном виде журнала.

Более того, тот же индекс **воссоздаётся при каждом старте службы**
(`db.ensure_positions_schema`), а `CREATE UNIQUE INDEX IF NOT EXISTS` смотрит
только на имя. Поправь миграцию и забудь службу — и первый же перезапуск вернул
бы прежнее правило молча. Поэтому правка сделана в **двух местах**, и это
закреплено тестом `test_the_relaxation_is_scoped_to_version_seven_in_both_places`.

## 3. Решения там, где ТЗ допускает два прочтения

Названы прямо, а не спрятаны в коде.

### 3.1. A1 и A4 читаются друг против друга — разрешено в пользу A4

A1 требует оставить `POSITION_MAX_OPEN` в `.env` со значением 0 = «без
ограничения» и закрепить тестом, что код трактует 0 именно так. A4 требует
**удалить** причину отказа вместе с проверкой, не оставляя мёртвой ветки.
Выполнить буквально оба нельзя: сохранённая проверка `max_open > 0 && …` — это
и есть та ветка, которую A4 запрещает.

**Сделано по A4:** проверки нет ни одной, причина `slots_full` и параметр
`max_open` удалены из правила целиком. Требование A1 выполнено так:

* значение по умолчанию и в `.env` — `POSITION_MAX_OPEN=0`;
* его печатает строка запуска службы (§9 ТЗ);
* тест `test_zero_max_open_means_no_limit_and_not_zero_positions` закрепляет,
  что ноль **не** превращается в «ноль позиций»: проверяется отсутствие
  параметра и причины, а не мягкость условия;
* **ненулевое значение не молчит**: служба пишет при старте
  `positions_setting_ignored=1` с именем настройки и причиной. Человек,
  поставивший «3», узнаёт, что число не работает, сразу, а не по расхождению
  журнала с ожиданием через неделю.

Валидатор, запрещающий ненулевое значение, **не** заведён намеренно: `.env`
из резервной копии (`.env.backup-v7`) содержит `POSITION_MAX_OPEN=5`, и такой
валидатор уронил бы все службы при откате по §10.

### 3.2. Три случая §9 — прочтение, при котором они непротиворечивы

Дословно §9 просит: «две одновременные позиции по одному токену открываются;
третья в ту же минуту отклоняется с причиной `token_pause`; через 60 минут
после открытия первой — открывается». Буквально «две в одну минуту» никакое
правило паузы дать не может: пауза либо держит токен, либо нет.

**Прочитано так:** по одному токену **одновременно открыты** две позиции (одна
открыта час назад и жива — срок жизни 48 часов, — вторая открывается сейчас);
кандидат **в ту же минуту** отклоняется с `token_pause`; через 60 минут после
последнего открытия вход снова разрешён. Именно это воспроизведено на стенде
(§7 отчёта) и закреплено тестом.

Следствие, о котором стоит сказать прямо: **пауза начинает действовать
немедленно, в той же итерации**. Кандидатов по одному токену в одной итерации
бывает несколько (сигналы моложе 180 секунд), и не отмечай служба открытие
сразу — они вошли бы пачкой, а пауза придерживала бы только одиночек. Антиспам,
пропускающий пачку, — это не антиспам.

### 3.3. Пауза не смотрит на версию логики

Правило сформулировано как «по этому же **токену** позиция уже открывалась».
Версия в отборе не участвует: две позиции по одному токену в одну минуту — это
две сделки по одному токену в одну минуту, чем бы их правила ни отличались.
Практическое следствие одно и малое: сразу после развёртывания живая позиция
версии 6 может задержать первый вход версии 7 по тому же токену максимум на час.

### 3.4. §5 C6 — упоминания слотов в `/status` не было

ТЗ просит «убрать упоминание слотов» из `/status`. Их там не было: слоты
упоминались в `/positions`. Убрано и добавлено следующее:

* в `/status` — новый раздел «Сделки (виртуальные)»: число открытых позиций с
  оговоркой «число не ограничено» и состояние пауз по токенам с остатком в
  минутах; выключенная пауза названа вслух (иначе контрольный опыт §9 было бы
  не отличить от обычного дня);
* в `/positions` — строка капитала при нулевом бюджете читается «занято X USDT
  (слот 2.00, бюджет не ограничен)» вместо «занято X из 0.00 USDT»;
* переводы причин `instrument_busy` и `slots_full` удалены, добавлен
  `token_pause`. Тест требует, чтобы перечень переводов **совпадал** с перечнем
  причин: причина без перевода превращает сводку в машинный ключ, перевод без
  причины описывает ограничение, которого нет.

## 4. Что изменено, по разделам ТЗ

### §3 A1, A2, A4 — оба ограничителя числа сделок сняты

* `src/positions/rules.py` — из `should_open` удалены параметры
  `has_open_position`, `open_count`, `max_open` и причины `REASON_INSTRUMENT_BUSY`,
  `REASON_SLOTS_FULL`. Перечень причин: было 10, стало 9.
* `src/core/db.py` — из отбора кандидатов удалено условие «по инструменту нет
  открытой позиции». Условие «один сигнал — не больше одной позиции» **оставлено**:
  оно не про частоту сделок, а про повторное чтение того же сигнала после
  перезапуска.
* `src/positions/runner.py` — исчезли `busy` и `open_count`.

### §3 A3 — капитал

* `POSITION_BUDGET_USD = 0` означает «без ограничения»: свободный капитал равен
  `math.inf`, и вычитание слота из бесконечности остаётся бесконечностью —
  особый случай в коде не понадобился.
* `POSITION_SLOT_USD = 2.0` не тронут. Прибыль по-прежнему не реинвестируется.
* Причина `no_free_capital` и её счётчик **сохранены** и стали недостижимы:
  счётчик обязан показывать ноль, и `deploy/verify_7.sh` считает ненулевое
  значение блокирующей находкой — оно означало бы, что бюджет снова конечен.
* Валидатор старта ослаблен ровно на ноль: значения **строго между** нулём и
  размером слота по-прежнему роняют службу на старте.

### §4 — пауза по токену

* Новая настройка `POSITION_TOKEN_PAUSE_MIN = 60` (0 выключает; отрицательное
  значение отвергается на старте).
* Чистая функция `token_pause_left_sec(last_open_age_sec, token_pause_sec)` —
  она же считает остаток для журнала, чтобы два выражения для одного числа не
  разошлись.
* Новая причина `token_pause`. Отсчёт ведётся **от открытия**: функция не знает
  о закрытии вовсе, и это закреплено тестом — при отсчёте от закрытия правило
  снова зависело бы от длительности сделки и блокировало бы токен почти на двое
  суток.
* Граница нестрогая в пользу входа: ровно 60 минут — вход разрешён.
* Каждый отказ пишется строкой `positions_skipped=1` с токеном, вероятностью
  сигнала, остатком паузы в секундах и действующим значением настройки.
* Новый запрос `db.get_last_open_ts_by_instrument(since)` — одно чтение на
  итерацию; при выключенной паузе запрос не делается вовсе.

### §5 — уведомления только по сделкам

* `src/notify/agent.py` — граница записана **версией логики**, а не отдельным
  выключателем: `SIGNAL_NOTIFY_MAX_LOGIC_VERSION = 6`. Причина: откат по §10
  состоит из возврата `.env` и `LOGIC_VERSION=6`, и сигнальные уведомления
  обязаны вернуться вместе с ним без правки кода; отдельный выключатель в `.env`
  однажды переставили бы, не заметив, что в поток вернулись десятки сообщений.
* Очередь сигналов **обрабатывается по-прежнему**: каждый сигнал «поглощается»
  (`notified = TRUE`, `notified_at` не ставится — отправки не было). Просто
  перестать читать очередь было бы хуже молчания: неотправленные сигналы
  копились бы в выборке вечно.
* Сводка придержанных сигналов тоже не уходит — это сообщение о сигналах.
  Очередь сводки истекает сама (TTL два часа).
* `NOTIFY_HOLD_MIN`, `NOTIFY_MAX_PER_HOUR`, `NOTIFY_COOLDOWN_SEC`,
  `NOTIFY_MIN_PROBABILITY`, `NOTIFY_MIN_AGENTS` — **значения не изменены**,
  код `should_notify` и `rate_limit_reason` не тронут (§5 C4).
* Суточная сводка (§5 C2) добавлена **разделом** в существующую сводку 06:00 UTC
  (`src/health/daily_report.py`, `section_positions_24h`): открыто, закрыто, итог
  за сутки в долларах, доля прибыльных, отказы `token_pause`, открыто на момент
  сводки. Новая рассылка не заводится — этап сокращает число потоков.
  Закрытия по пробелу в данных исключены из итога и доли, но их число названо.
* Ограничителя частоты на сообщения о сделках нет и не ставится (§5 C5); тест
  проверяет, что в службу позиций не попало ни одно имя `NOTIFY_*`.

**Отказов `token_pause` в сводке названо два числа, а не одно.** Счётчик
заведён на календарные сутки UTC, а сводка выходит в 06:00 UTC — её «последние
24 часа» приходятся на два ключа. Сложить их значило бы подписать «за сутки»
сумму за тридцать часов, поэтому названы оба, каждый своей датой.

### §9 — строка запуска

Служба печатает при старте все восемь величин, названных ТЗ поимённо:
`logic_version=7 max_open=0 token_pause_min=60 budget_usd=0.0 slot_usd=2.0
max_hold_hours=48 plus_wait_start_hours=24 min_probability=0.8`. Перечень
вынесен в `startup_fields()` — проверить состав можно только когда его собирает
одно место, а не форматная строка внутри вечного цикла.

## 5. База данных

### 5.1. Миграция нужна была — и вот почему (ответ на §7.2)

ТЗ просит исполнителя проверить схему самому и, если ограничения нет, написать
об этом прямо. **Ограничение есть.** Правило «один инструмент — одна открытая
позиция» записано частичным уникальным индексом
`ux_positions_one_open_per_instrument` (миграция 018), поэтому миграция
обязательна.

### 5.2. Миграция 027 — следующий свободный номер

`db/migrations/027_positions_token_pause.sql` и
`db/migrations/027_positions_token_pause_rollback.sql`.

Что делает: снимает индекс со старым определением и создаёт его заново с
условием `WHERE status = 'open' AND logic_version < 7`. Строки версий 5 и 6
остаются под тем же запретом, под которым открывались. Миграция обёрнута в
`BEGIN … COMMIT`, идемпотентна, **не содержит ни одного UPDATE, DELETE или
INSERT** — проверено тестом по исполняемым строкам.

Индекс `ux_positions_signal` не тронут.

Проверено на настоящей PostgreSQL 16:

```
до:      ... (instrument_id) WHERE (status = 'open')
после:   ... (instrument_id) WHERE ((status = 'open') AND (logic_version < 7))
дважды:  повторный прогон ничего не меняет (NOTICE: already exists, skipping)
откат:   ... (instrument_id) WHERE (status = 'open')
```

Откат при двух открытых позициях версии 7 по одному токену **отказывается
работать** и не меняет ни одной строки:

```
ERROR: откат 027 невозможен: по 1 токенам сейчас открыто больше одной позиции.
Прежний индекс такие строки не допускает, а закрыть их выдуманной ценой или
удалить откат не вправе. Дождитесь закрытия по сроку и повторите
```

### 5.3. Новых колонок и таблиц нет

Пауза по токену — правило кода над уже имеющейся колонкой `opened_at`. Отдельная
отметка была бы вторым источником истины о том же факте.

### 5.4. `EXPORT_LOGIC_VERSION` — правки не потребовалось (ответ на §7.4)

Говорю прямо, как требует ТЗ по аналогичному поводу. Очередь **торгового
журнала** отбирает позиции по отметкам `sheet_opened_at` / `sheet_closed_at` и
не содержит условия по версии логики ни одного: сделки версии 7 попадут в лист
сразу, как появятся, а строки версии 6 останутся на месте — ни одна выгрузка их
не трогает. Заметка при открытии уже печатает правило строкой «без предела ·
правило v7», взяв номер из самой позиции.

`EXPORT_LOGIC_VERSION=current` управляет **листами сигналов** и означает
«последняя открытая версия из `logic_version_windows`»; границу версии 7
зафиксирует Decision Agent при первом старте на ней. Значение менять **не нужно
и нельзя**: число 6 в нём удержало бы листы сигналов на прошлой версии.
Закреплено тестом `test_the_trade_journal_takes_every_version_and_deletes_nothing`.

## 6. Тесты

Новый набор — `tests/test_logic_7.py`, 33 теста (один требует базы: без `AT_TEST_DSN` пропускается).
Обновлены `tests/conftest.py` (`CURRENT_LOGIC_VERSION = 7`) и три набора,
закреплявших снятые правила: 9.1, 9.1.1, 9.2. В каждом случае проверка не
ослаблена, а переписана на то, что этап действительно утверждает, — например,
тест «один инструмент — одна позиция» стал тестом «этого правила больше нет, и
нет насовсем».

Что закреплено сверх очевидного:

* ноль в `POSITION_MAX_OPEN` не превращается в «ноль позиций» — отсутствием
  параметра и причины, а не мягкостью условия;
* условие «инструмент занят» ушло **и из запроса** отбора кандидатов: оставь его
  там — и не изменилось бы ничего, кандидат просто не дошёл бы до правила;
* пауза считается от открытия — тем, что функция не знает о закрытии вовсе;
* пауза по одному токену не держит остальные (иначе пять токенов давали бы одну
  сделку в час на всех);
* ослабление индекса записано в **двух** местах — в миграции и в
  `ensure_positions_schema`;
* перечень переводов причин в боте совпадает с перечнем причин в правиле —
  в обе стороны.

## 7. Стенд: три случая §9 и контрольный опыт

Прогон на настоящей PostgreSQL 16, настоящей службой позиций
(`open_new_positions`), с реальными свечами, сигналами и замороженными целями.
Отправка в Telegram на стенде отключена.

```
итерация 1                    opened=1  candidates=1  refusals={}
итерация 2 (та же минута)     opened=0  candidates=1  refusals={'token_pause': 1}
                              журнал: reason=token_pause pause_left_sec=3480
                                      probability=0.9 symbol=STAND/USDT
итерация 3 (+60 минут)        opened=1  candidates=1  refusals={}

позиций по токену: 2, из них открытых: 2
  id=3 logic_version=7 status=open opened_at=11:58
  id=4 logic_version=7 status=open opened_at=12:58

контрольный опыт (POSITION_TOKEN_PAUSE_MIN=0)
                              opened=2  candidates=2  refusals={}
```

Все три случая §9 воспроизведены: две одновременные позиции по одному токену
существуют; кандидат в ту же минуту отклонён с `token_pause`; через 60 минут
вход разрешён. Контрольный опыт даёт ноль отказов при выключенной паузе и
больше нуля при включённой — то есть опыт, который обязан упасть, падает.

## 8. Что проверяется только на сервере

Эти критерии §9 стендом не проверить — они о боевых данных и боевом Telegram:

1. **Итог версии 5 не изменился:** −$0.68088 на 88 сделках, до цента.
   Проверяет `deploy/verify_7.sh`, раздел 4, и считает расхождение блокирующим.
2. **В Telegram не приходит ни одного сообщения о сигнале**, приходят открытия и
   закрытия. Косвенно проверяет тот же скрипт (`notified_at` за сутки), прямо —
   владелец глазами.
3. **Поток сигналов в базу не изменился** больше естественного разброса.
   Скрипт печатает число сигналов за последний час и за предыдущий; провал до
   нуля считает блокирующим.
4. **Первые 10 строк версии 7 в торговом журнале** — на съезд разметки столбцов
   (известный дефект с поз. 73 версии 5). Смотрит владелец: автоматически это не
   проверяется ничем, и говорить обратное было бы неправдой.

## 9. Предсказания зафиксированы до прогона

Записаны в ТЗ §8 и здесь не пересматриваются: 10–40 сделок в сутки; больше
половины отклонённых кандидатов — по `token_pause`; поток пачками; доля
прибыльных около 43%. Числа для сверки даст сводка и `/positions`.

Отдельно отмечу арифметику, которая понадобится при разборе: верхняя граница при
пяти токенах и часовой паузе — 120 сделок в сутки, и она недостижима, потому что
сигнал обязан пройти порог 0.8 и полный кворум.

---

## 10. Риски, названные заранее

* **Пауза считается от открытия последней позиции по токену любой версии.**
  Сразу после развёртывания живая позиция версии 6 может задержать первый вход
  версии 7 по тому же токену не более чем на час.
* **Открытых позиций станет много.** Ни число, ни капитал больше ничем не
  ограничены; при 40 сделках в сутки и сроке 48 часов одновременно открытых
  может быть несколько десятков. Служба читает окно баров по каждой открытой
  позиции на каждой итерации — это тысячи строк в минуту при пяти позициях и
  десятки тысяч при пятидесяти. На минутном шаге запас есть, но за нагрузкой
  на первой неделе стоит посмотреть.
* **Сообщений о сделках станет столько же, сколько сделок.** Это заказано
  явно (§5 C5), и ограничителя нет.
* **Откат частичный оставляет систему в несогласованном виде.** Служба позиций
  при каждом старте приводит индекс к виду версии 7, поэтому откат базы без
  отката образа продержится до ближайшего перезапуска. Откатывать нужно целиком:
  `.env`, версию логики и миграцию.

## 12. Откат

1. Вернуть `/opt/agent-trade/.env.backup-v7` на место `.env` (в нём
   `LOGIC_VERSION=6`, `POSITION_MAX_OPEN=5`, `POSITION_BUDGET_USD=10.0`).
2. Откатить миграцию 027. Если по какому-то токену открыто больше одной
   позиции версии 7, откат **откажется** работать и скажет об этом; дождитесь
   закрытия по сроку (48 часов) и повторите.
3. Развернуть прежний образ и перезапустить. Без этого шага служба при старте
   снова ослабит индекс.

Данные версии 7 при откате **не удаляются**: сделки состоялись и измерены.

## 13. Команды владельцу — по одной, по порядку

Выполнять на сервере под пользователем `agent`, из каталога `/opt/agent-trade`.

**1. Резервная копия настроек (до любых правок):**
```
cp /opt/agent-trade/.env /opt/agent-trade/.env.backup-v7
```

**2. Проверить, что копия сделана:**
```
ls -l /opt/agent-trade/.env.backup-v7
```

**3. Забрать код:**
```
cd /opt/agent-trade && git pull
```

**4. Записать итог версии 5 ДО миграции (понадобится для сверки):**
```
docker compose exec -T postgres psql -U agenttrade -d agenttrade -tA -c "SELECT count(*), round(sum(net_pnl_usd),5) FROM positions WHERE logic_version=5 AND status='closed' AND exit_reason<>'data_gap';"
```

**5. Применить миграцию 027:**
```
docker compose exec -T postgres psql -U agenttrade -d agenttrade < db/migrations/027_positions_token_pause.sql
```

**6. Убедиться, что индекс ослаблен только для версии 7:**
```
docker compose exec -T postgres psql -U agenttrade -d agenttrade -tA -c "SELECT indexdef FROM pg_indexes WHERE indexname='ux_positions_one_open_per_instrument';"
```

**7. Правка `.env` — версия логики:**
```
sed -i 's/^LOGIC_VERSION=.*/LOGIC_VERSION=7/' /opt/agent-trade/.env
```

**8. Правка `.env` — снятие потолка позиций:**
```
sed -i 's/^POSITION_MAX_OPEN=.*/POSITION_MAX_OPEN=0/' /opt/agent-trade/.env
```

**9. Правка `.env` — бюджет без ограничения:**
```
sed -i 's/^POSITION_BUDGET_USD=.*/POSITION_BUDGET_USD=0/' /opt/agent-trade/.env
```

**10. Правка `.env` — пауза по токену (строка новая, поэтому дописывается):**
```
grep -q '^POSITION_TOKEN_PAUSE_MIN=' /opt/agent-trade/.env || echo 'POSITION_TOKEN_PAUSE_MIN=60' >> /opt/agent-trade/.env
```

**11. Проверить получившиеся значения:**
```
grep -E '^(LOGIC_VERSION|POSITION_MAX_OPEN|POSITION_BUDGET_USD|POSITION_TOKEN_PAUSE_MIN|POSITION_SLOT_USD|POSITION_MIN_PROBABILITY|POSITION_MAX_HOLD_HOURS|POSITION_PLUS_WAIT_START_HOURS)=' /opt/agent-trade/.env
```

**12. Пересобрать образы:**
```
docker compose --profile "*" build --no-cache
```

**13. Поднять службы:**
```
docker compose --profile "*" up -d
```

**14. Прочитать строку запуска службы позиций:**
```
docker compose logs --since 10m --no-color positions | grep token_pause_min | tail -1
```

**15. Прогнать проверку развёртывания:**
```
sudo -u agent bash /opt/agent-trade/deploy/verify_7.sh
```

**16. Через час — посмотреть, что происходит со сделками:**
```
docker compose exec -T postgres psql -U agenttrade -d agenttrade -tA -c "SELECT count(*) FILTER (WHERE opened_at > now() - interval '1 hour'), count(*) FILTER (WHERE status='open') FROM positions WHERE logic_version=7;"
```

**17. Через час — посмотреть, сколько режет пауза:**
```
docker compose exec -T redis redis-cli GET "positions:refused:7:$(date -u +%F):token_pause"
```

**18. Контрольный опыт (§9 ТЗ) — выключить паузу на время:**
```
sed -i 's/^POSITION_TOKEN_PAUSE_MIN=.*/POSITION_TOKEN_PAUSE_MIN=0/' /opt/agent-trade/.env && docker compose up -d positions
```

**19. Контрольный опыт — вернуть паузу обратно:**
```
sed -i 's/^POSITION_TOKEN_PAUSE_MIN=.*/POSITION_TOKEN_PAUSE_MIN=60/' /opt/agent-trade/.env && docker compose up -d positions
```
