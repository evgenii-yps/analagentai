## 1. ЗАДАЧА 1 (СРОЧНО). Пункт Б6 — критерий по фактическому разрешению строки

**Что сделано.** В разделе 6 `deploy/verify_9_1.sh` предикат заменён в ОБОИХ
запросах (счёт и разбивка) на разрешение-зависимый:

```sql
computed_at < entry_ts
              + make_interval(hours => horizon_h::int)
              + make_interval(secs => CASE resolution
                                        WHEN '1m' THEN 60
                                        WHEN '1h' THEN 3600
                                        ELSE ${settle_sec}
                                      END)
```

Формула держится в одной переменной `unsettled_where` и подставляется в оба
запроса: три копии разошлись бы при первой правке. Вычисление `settle_sec` из
`.env` оставлено и работает теперь ветвью `ELSE` — страховка на случай третьего
разрешения.

Пояснения раздела приведены в соответствие: вместо «запас закрытия последнего
бара: 3900 с» печатается, что запас берётся по колонке `resolution` (60 с для
`1m`, 3600 с для `1h`, `${settle_sec}` с для неизвестного), и отдельно —
что `${settle_sec}` относится ТОЛЬКО к неизвестному разрешению.

Добавлена разбивка строк по разрешениям — печатается ВСЕГДА, а не только при
находке: без неё «подозрительных 0» не отличить от «строк нет вовсе».

Разбивка находки расширена столбцом `resolution`: именно оно задаёт, сколько
строке полагалось ждать.

**Чем проверено.** `bash -n` — синтаксис. SQL пункта выполнен на настоящей
PostgreSQL 16 против трёх подложенных строк:

| строка | `resolution` | запас после срока | вердикт |
|---|---|---|---|
| `grid_buy` | `1m` | 61 с | чисто |
| `grid_sell` | `1h` | 61 с | **подозрительна** |
| `grid_buy` | `1h` | 3601 с | чисто |

Счёт запроса — `1`. Разбивка по разрешениям — `1h│2`, `1m│1`. Тот же случай
проверяется тестом §7.7 (`test_a_minute_row_is_clean_where_the_same_hour_row_is_suspicious`).

## 2. ЗАДАЧА 2 (СРОЧНО). Критерий в скрипте починки и три ограждения

**2.1. Критерий.** `Database.STRATEGY_UNSETTLED_PREDICATE` в `src/core/db.py`
заменён на разрешение-зависимый с `ELSE $1::int`. Предикат остался в ОДНОМ
экземпляре: оба режима скрипта и все три метода
(`count_/get_/delete_strategy_outcomes_unsettled`) спрашивают его. Сигнатуры не
менялись — параметр `settle_seconds` остался и означает теперь запас для
неизвестного разрешения; вызовы в `scripts/repair_9_1_strategy_settle.py` не
тронуты. Докстринги трёх методов переписаны, чтобы новое значение параметра не
приходилось выводить из кода.

В отчёт скрипта добавлены разбивка по разрешению и столбец `разр.` в примерах.

**2.2. Три ограждения `--apply`.**

1. **Обязательный снимок.** `DELETE` выполняется только после успешной записи
   снимка «до». Исключение при записи ловится, печатается причина и путь,
   возвращается **код 3**, ничего не удаляется.
2. **Подтверждение числом.** `--confirm-count=N` обязателен при `--apply` и
   проверяется ДО подключения к базе (забытый аргумент обязан останавливать на
   пороге). Перед удалением счёт снимается ЗАНОВО; при расхождении печатаются
   оба числа и возвращается **код 4**. `--confirm-count` без `--apply` —
   ошибка аргументов.
3. **Ноль — не повод работать.** При нуле подозрительных строк печатается
   «удалять нечего», транзакция не открывается, **код 0**.

Шапка скрипта переписана: новый критерий с объяснением, почему `settle_seconds()`
остался запасом для неизвестного разрешения, примеры вызова с `--confirm-count`
и таблица кодов возврата.

Подсказка в `verify_9_1.sh` приведена в соответствие: сначала команда РЕЖИМА
ПОДСЧЁТА, и только потом — удаление с `--confirm-count=${bad}`, где `${bad}` —
то самое число, что напечатано строкой выше.

**Чем проверено.** На живой PostgreSQL, на настоящих строках:

```
--apply без --confirm-count           → код 2 (отказ разбора аргументов)
--apply --confirm-count=7 (факт 1)    → код 4, строк в таблице по-прежнему 3
--apply --confirm-count=1 (факт 1)    → код 0, удалена 1 строка
```

Плюс четыре теста на ПОДМЕНЁННОМ слое доступа к базе, где проверяется ФАКТ
невызова `delete`, а не текст вывода: несовпавшее число (код 4, `deleted_calls == 0`,
снимок даже не снимался), совпавшее число (код 0, удаление произошло), упавший
снимок (код 3, `deleted_calls == 0`), ноль строк (код 0, ни снимка, ни удаления).

## 3. ЗАДАЧА 3 (СРОЧНО). Пункт 9 — причины отказа только из строк отказа

**Что сделано.** Реализовано ровно как в §3 ТЗ: сначала `grep 'positions_skipped=1'`,
и только потом извлечение `reason=` из отобранных строк. Пустой результат
печатается словами — «отказов не было», — потому что пустое место читатель
толкует как поломку скрипта.

**Чем проверено.** `bash -n`; логика совпадает с ручным подсчётом из критерия
приёмки §8.2 посимвольно (это тот же конвейер, применённый к отобранному
подмножеству).

**Оговорка, которую надо знать.** Проверить это на настоящем журнале
не удалось — доступа к серверу нет. При этом в контейнере `stdout` не TTY, и
`src/core/logging.py` в этом случае включает `JSONRenderer`, где поле выглядит
как `"reason": "no_fresh_bar"`, а не `reason=no_fresh_bar`. На JSON-журнале
шаблон `reason=[a-z_]*` не найдёт ничего — ни до правки, ни после. Это НЕ
делает правку бесполезной (она верна для обоих случаев: причина теперь берётся
только из строк отказа), но означает, что при JSON-журнале пункт 9 покажет
пустую разбивку. Проверяется одной командой на сервере:

```
sudo -u agent docker compose logs --since 24h --no-color positions \
    | grep 'positions_skipped=1' | head -3
```

Если строки — JSON, шаблон в пункте 9 надо будет расширить до
`'"reason": "[a-z_]*"'`. Менять его на догадку сейчас исполнитель не стал:
ТЗ задаёт шаблон дословно, а угадывать формат чужого журнала, не видя его, —
это ровно тот способ «починить», после которого никто не знает, что проверяется.

## 5. ЗАДАЧА 5. Учёт капитала и причина `no_free_capital`

**Настройка.** `POSITION_BUDGET_USD: float = 10.0` с `model_validator(mode="after")`:
бюджет меньше слота — падение на старте с сообщением, называющим обе величины.
Проверка сделана валидатором модели, а не пополевым: участвуют два поля сразу, и
пополевой валидатор сделал бы порядок объявления полей частью правила. Переменная
внесена в `.env.example` с объяснением, почему прибыль не реинвестируется.

**Правило.** `REASON_NO_FREE_CAPITAL = "no_free_capital"` добавлена в
`REFUSAL_REASONS`; в `should_open` добавлены `free_capital_usd` и `slot_usd`,
проверка стоит ПОСЛЕ `slots_full` и ДО `no_fresh_bar`. Сравнение нестрогое в
пользу входа: денег ровно на слот — слот оплачен целиком.

**Сервис.** Занятый капитал считается из ТОГО ЖЕ единственного чтения
`get_open_positions()`, что и занятые инструменты; `free_capital = POSITION_BUDGET_USD − committed`;
после успешного открытия уменьшается на `POSITION_SLOT_USD`. Накопленный итог к
бюджету не прибавляется нигде.

**Бот.** `BotQueries.positions_capital()` возвращает `committed_usd` и
`realized_usd` (последний — за всё время, ИСКЛЮЧАЯ закрытия с `exit_reason = 'data_gap'`).
В `render_positions` под заголовком печатаются две строки:

```
Капитал: занято 4.00 из 10.00 USDT (слот 2.00)
Накопленный итог: +0.031234 USDT (не реинвестируется)
```

Слово «виртуально» из заголовка не убрано.

**Чем проверено.** Шесть тестов: отказ по деньгам (включая отрицательный
остаток и границу «ровно на слот»); порядок «слоты важнее денег»; порядок
«деньги важнее свежести свечи»; валидатор бюджета; текстовая проверка того, что
в формуле свободного капитала НЕТ накопленного итога (доказывать надо
ОТСУТСТВИЕ слагаемого — значением его не поймать: при нулевом итоге обе формулы
дают одно число); формат двух строк бота. Плюс живой прогон: `positions_capital()`
на базе с одной закрытой по пробелу позицией вернул `realized_usd = 0.0`.

**Замечание к §5.3 ТЗ, которое подтвердилось.** При действующих значениях
(10 / 2 / 5) причина `no_free_capital` не сработает никогда: деньги и слоты
кончаются одновременно. Ограждение поставлено ради того дня, когда слот или
бюджет изменят. Это записано комментарием в коде, чтобы следующий читатель не
принял недостижимую ветку за мёртвый код и не удалил её.

## 6. ЗАДАЧА 6. Закрытие позиции при пробеле в данных

**Миграция 019** (`db/migrations/019_positions_data_gap.sql` + откат):
`positions_reason_chk` пересоздаётся с пятым значением `data_gap`.
Идемпотентна. Откат сначала считает строки с `data_gap` и при ненулевом счёте
`RAISE EXCEPTION` с объяснением — не выполняется вовсе.

**Схема, которую сервис гарантирует при старте, тоже знает `data_gap`.** Это
сверх буквы ТЗ, и вот зачем: `POSITIONS_CHECKS` в `src/core/db.py` создаёт
ограничение на ЧИСТОМ томе, где миграций ещё не было, и перечень из четырёх
значений отверг бы первое же закрытие по пробелу. Отдельным блоком
`ensure_positions_schema` чинит и уже СУЩЕСТВУЮЩЕЕ ограничение, если оно ещё не
знает `data_gap` (миграция могла быть не применена на работающем томе).
Пересоздаётся оно только при необходимости: безусловный `DROP/ADD` на каждом
старте оставлял бы таблицу на доли секунды без закрытого перечня причин.

**Настройка.** `POSITION_GAP_GRACE_SEC: int = 7200`, внесена в `.env.example`.

**Правило.** `check_gap_exit` в `src/positions/rules.py` — чистая функция, без
базы и без `datetime.now()`. Возвращает `None`, пока `now < deadline_at + grace`.
Цена выхода — `close` последнего бара, открывшегося СТРОГО раньше срока; если
таких баров нет — `entry_price`. `exit_bar_ts` — метка того же бара, либо
`deadline_at`. `outcome_certain = False` всегда. `mae/mfe/bars_held` — по
фактически виденным барам.

**Сервис.** В `sync_open_positions`:

* условие пропуска ослаблено до `settle_edge <= last_checked AND now < gap_deadline`
  — без этого правило не сработало бы НИКОГДА, потому что позиция без новых
  баров и есть позиция с пропавшими данными;
* пустой ряд баров больше не выходит из цикла: `check_exit` спрашивается только
  когда есть о чём спрашивать, а `check_gap_exit` — всегда, когда исхода нет;
* `closed_at = now` для `data_gap` (позиция закрыта истечением ожидания, а не
  событием на графике);
* в журнал идёт `positions_data_gap=1` уровня **warning** с `position_id`,
  `symbol`, `last_bar_ts`, `gap_sec`, `grace_sec`, и следом обычная строка
  `positions_closed=1` с `exit_reason=data_gap`;
* причина учитывается в `ClosedStats.by_reason`.

**Сообщение.** Отдельный `messages.data_gap_text`, не переиспользующий
`closed_text`. Различает два случая: бары были (называет момент последней
известной цены) и баров не было вовсе (говорит, что выход посчитан по цене
входа, — ссылаться на «последнюю известную цену», которой не существовало,
значило бы выдумать наблюдение).

**Статистика.** `avg(net_pnl_pct)`, `sum(net_pnl_usd)`, `avg(entry_slippage_pct)`
считаются с `FILTER (WHERE exit_reason <> 'data_gap')`; добавлен
`count(*) FILTER (WHERE exit_reason = 'data_gap') AS data_gap`. В `render_positions`
строка «Закрыто по пробелу в данных: N (в средние не входят)» печатается только
при N > 0. Те же `FILTER` поставлены в `db.get_positions_summary` и в разделе 8
`verify_9_1.sh` — иначе бот и проверка показывали бы разные средние по одной
таблице. В `verify_9_1.sh` добавлен вывод числа `data_gap` за сутки (печатается
всегда, включая ноль) с разбивкой по инструментам и предупреждением при N > 0.

**Чем проверено — живым прогоном сервиса на настоящей базе.** Позиция открыта
28.08 12:00, срок 29.08 12:00, три бара сразу после входа, дальше данных нет.

| момент | результат |
|---|---|
| срок + 1 ч (запас 2 ч не выдержан) | `closed=0`, `touched=1`, статус `open` |
| срок + 3 ч | `closed=1`, `by_reason={'data_gap': 1}` |

Строка в базе: `exit_reason='data_gap'`, `exit_price=100.5` (close последнего
виденного бара), `outcome_certain=False`, `bars_held=3`, `closed_at == now`
(проверено равенством). В журнале — `positions_data_gap=1 gap_sec=97020
last_bar_ts=2026-08-28T12:03:00+00:00`. Сообщение — отдельного вида. Бот:
`positions_capital → realized_usd = 0.0`; `positions_summary → closed=1,
data_gap=1, avg=None, sum=None`.

Тот же прогон БЕЗ ЕДИНОГО БАРА: `exit_price = entry_price = 100.0`,
`bars_held=0`, `net_pnl_pct = −0.22` — **ровно минус издержки**, `closed_at == now`.

Миграция 019 применена дважды подряд, откачена и применена снова на настоящей
PostgreSQL 16; после каждого шага читалось фактическое определение ограничения,
а не код возврата psql. Отказ отката при живых строках `data_gap` проверен
отдельно, вместе с тем, что после неудачи ограничение осталось на месте и
по-прежнему знает пять значений.

## 8. НАЙДЕННЫЕ ОШИБКИ В ТЗ

### 8.1. §7.9: у причин ОТКАЗА нет и не может быть ограничения в миграциях

§7.9 требует сверить с ограничениями миграций 018 и 019 ОБА перечня —
`EXIT_REASONS` и `REFUSAL_REASONS`. Для `EXIT_REASONS` это возможно и сделано:
они лежат в колонке `positions.exit_reason` и закрыты `positions_reason_chk`.

`REFUSAL_REASONS` не записываются НИ В ОДНУ таблицу. Отказ во входе означает,
что строки позиции не появилось вовсе; причина живёт только в журнале
(`positions_skipped=1 reason=…`). Ограничения для неё нет ни в 018, ни в 019,
ни где-либо ещё, и сверять её с миграциями не с чем.

**Что сделано вместо.** Для `EXIT_REASONS` сверка сделана СТРОЖЕ, чем просят: не
«каждое значение встречается в тексте», а равенство МНОЖЕСТВ с перечнем в
ограничении 019 — лишнее значение в ограничении так же опасно, как
недостающее, оно разрешило бы записать причину, которой код не знает. Отдельно
сверяется 018 (четыре значения) и схема, которую сервис гарантирует при старте.

Для `REFUSAL_REASONS` проверяется то, что проверить можно: перечень закрыт,
содержит ровно десять значений без повторов, и ни одно из них в миграциях НЕ
встречается — то есть отсутствие сверки не следствие того, что её забыли
написать. Если отказы когда-нибудь начнут записываться в базу, этот тест
покраснеет и потребует настоящей сверки. Всё это записано прямо в докстринге
теста `test_refusal_reasons_stay_a_closed_list_of_ten`.

### 8.2. §8.7: mypy в конфигурации проекта не настроен

Критерий приёмки требует, чтобы «ruff и mypy в конфигурации проекта» были
чисты. Конфигурации mypy в проекте НЕТ: ни секции в `pyproject.toml`, ни
`mypy.ini`, ни зависимости в `[project.optional-dependencies].dev`, ни шага в
`.github/workflows/ci.yml` (там только `ruff check .` и `pytest`).

**Что сделано вместо.** mypy запущен с настройками по умолчанию

## 10. НАЙДЕННЫЕ ПРОБЛЕМЫ, В ТОМ ЧИСЛЕ ВНЕ ЭТАПА

### 10.1. Новый критерий уже́ прежнего на величину задержки коллектора

Формула §1 ТЗ даёт минутной строке запас ровно 60 секунд, а часовой — ровно
3600. `BARRIER_SETTLE_MINUTES` (5 минут) в них НЕ входит — он остался только в
ветке `ELSE`. Между тем сам этот параметр появился в Этапе 8.10.1 именно
потому, что коллектор дописывает закрывшуюся свечу НЕ МГНОВЕННО: `UPSERT` с
`DO UPDATE` может переписать её в течение нескольких секунд после закрытия.

Следствие: строка минутного ряда, посчитанная через 61–360 секунд после срока,
теперь считается исправной, хотя её последний бар в этот момент теоретически
ещё мог быть переписан. §7.7 ТЗ требует именно такого поведения дословно
(«через 61 секунду — НЕ подозрительна»), поэтому реализовано как написано.

Практического вреда, скорее всего, нет: по данным §0 минимальный фактический
запас в базе — четверть часа, то есть в это окно не попадает ни одна строка.
Но если критерий однажды соберутся ужесточить, начинать надо отсюда, а не с
разрешений: достаточно добавить `+ make_interval(mins => BARRIER_SETTLE_MINUTES)`
к обеим известным веткам.

### 10.2. `POSITION_GAP_GRACE_SEC` = 2 часа против суточного горизонта: закрытие по пробелу может опередить обычный `timeout`

Правило `check_gap_exit` срабатывает через 2 часа после срока. Обычный
`timeout` требует, чтобы бар срока был ПРЕДЪЯВЛЕН, — то есть при задержке
поступления данных дольше двух часов позиция, которая на самом деле дожила до
срока штатно, будет закрыта как `data_gap` вместо `timeout`, и её результат
уйдёт из статистики.

Это не дефект реализации (так написано в ТЗ), а свойство выбранного запаса:
он защищает от вечно висящих позиций ценой того, что длительный перебой сбора
данных превращает штатные исходы в неизмеренные. Величина `gap_sec` в журнале и
отдельная строка в `/positions` позволяют это заметить: если `data_gap`
появляются пачками с `gap_sec` чуть больше 7200, значит, запас надо поднимать, а
не искать ошибку в правиле.

### 10.3. Позиция, чей инструмент «ожил» после закрытия по пробелу, второй раз не откроется

Индекс `ux_positions_signal` уникален по `signal_id`, и повторного входа по тому
же сигналу не будет — это правильно. Но стоит знать: закрытие по пробелу
безвозвратно. Если данные подъедут через сутки, восстановить настоящий исход
позиции будет уже нельзя — строка закрыта, `outcome_certain=False`, и пересчёта
для `positions` в проекте нет (в отличие от `strategy_outcomes`, где он
существует). Это осознанная цена освобождения слота, но она нигде в ТЗ не
названа.

### 10.4. Раздел 8 `verify_9_1.sh` считал средние по всем закрытиям

Обнаружено при выполнении §6.7: проверка считала `avg(net_pnl_pct)` и
`sum(net_pnl_usd)` по ВСЕМ закрытым позициям, и после появления `data_gap` она
показывала бы средние, отличные от бота. Исправлено теми же `FILTER`. Это
изменение сверх буквы §6.7 (там названы только `src/bot/queries.py` и
`render_positions`), но без него две части системы отвечали бы на один вопрос
по-разному.

### 10.5. `db.get_positions_summary` в `src/core/db.py` не используется никем

Метод существует с Этапа 9.1 и не вызывается ни из одного места (бот ходит
через `BotQueries`). Я привёл его `FILTER`-ы в соответствие с ботом, чтобы он не
стал источником расхождения, когда его наконец позовут, — но само по себе это
мёртвый код, и его стоит либо задействовать, либо убрать. Удалять на этом этапе
не стал: §0 не разрешает трогать лишнее, а метод не мешает.
