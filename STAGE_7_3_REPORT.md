## 1. Блок A — симметрия агентов

### 1.1 Причина односторонности Futures: установлена по коду

Разбор выполнен **до** правок, по файлу `src/agents/futures.py` версии `main`
(коммит `5be8027`). Ветку `bearish` в старом коде давали ровно два условия:

| Путь к `bearish` | Строки старого файла | Условие | Почему не выполнялось |
|---|---|---|---|
| ветка разворота | 73, 76, 78 | `is_extreme = abs(rate) > extreme_threshold` (0.0003), затем `signal = SIGNAL_BEARISH if rate > 0 else SIGNAL_BULLISH` | наблюдаемый \|funding\| по BTC/USDT на OKX на порядок ниже порога; правка Этапа 7.0 (0.0005 → 0.0003) разрыв уменьшила, но не устранила |
| ветка продолжения тренда | 87–89 | `elif oi_rising and rate < 0:` | требует **отрицательного** funding; у бессрочного фьючерса на BTC funding почти всегда положителен (лонги платят шортам) |

Ветку `bullish` при этом давали два симметричных по форме, но достижимых
условия: строка 78 при `rate < 0` (тоже недостижимо) и строка 82
`elif oi_rising and rate > 0:` — **достижимо всегда**. Остаток случаев уходил
в `neutral` (строка 93).

**Вывод: асимметрия была структурной — она следовала из кода, а не из рынка.**
Обе двери к `bearish` заперты абсолютной константой и знаком funding, обе двери
к `bullish` — нет. Наблюдение «11 185 выводов, 8 суток, три версии логики, ноль
bearish» — прямое следствие этих четырёх строк.

Это не реконструкция по совпадению: то же самое воспроизводится запуском старой
и новой функции на одних и тех же данных (funding целиком положительный, по
модулю ниже прежнего порога — то есть ровно те условия, что были на рынке):

| Сценарий (весь funding > 0, \|f\| < 0.0003) | OI | старый код | новый код |
|---|---|---|---|
| funding падает к минимуму недели | растёт | `bullish` | `bearish` |
| funding падает к минимуму недели | ровный | `neutral` | `bearish` |
| funding растёт к максимуму недели | растёт | `bullish` | `bullish` |
| funding растёт к максимуму недели | ровный | `neutral` | `bullish` |

Старый код на падающем к недельному минимуму funding выдавал **bullish** —
противоположное направление, — потому что смотрел только на знак.

### 1.2 Фактическое распределение funding rate

Гипотеза автора ТЗ («агент сравнивает funding с абсолютным порогом, а funding по
BTC почти всегда положителен») **подтверждается по коду полностью**. Численное
подтверждение по данным сервера у среды разработки получить нельзя: доступа к
продакшн-БД нет. Поэтому запрос распечатан пакетом и выполняется на сервере —
блок **2.11** в `analysis/sql/02_agents.sql`:

```

доля значений выше прежнего порога 0.0003
```

Заполняется по выводу (таблица оставлена пустой намеренно — данные с сервера):

| Показатель | Значение |
|---|---|
| N значений, период | |
| min / p1 / p5 | |
| медиана | |
| p95 / p99 / max | |
| доля отрицательных, % | |
| доля \|rate\| > 0.0003, % | |

Ожидание по коду и прежним отчётам: доля отрицательных ≈ 0 %, доля выше порога
≈ 0 %. Если факт разойдётся с ожиданием — это нужно записать как есть: причина
тогда не только в пороге.

### 1.3 Что изменено в Futures

Направление определяется положением текущего значения **относительно его
собственного распределения** за скользящее окно:

* перцентиль текущего funding в окне `FUTURES_LOOKBACK_HOURS` (168 ч);
* `bullish`, если перцентиль ≥ `FUTURES_PCT_HIGH` (0.80);
* `bearish`, если перцентиль ≤ `FUTURES_PCT_LOW` (0.20);
* иначе `neutral`;
* `confidence` — нормированное расстояние от границы нейтральной зоны, [0, 1];
* меньше `FUTURES_MIN_POINTS` (20) точек в окне → `insufficient_data`
  («нет данных»), а не `neutral` («данные есть, сигнала нет»).

Перцентиль считается «средним рангом» (доля строго меньших плюс половина
равных). Именно эта форма делает правило **точно антисимметричным**: при
зеркальном отражении выборки перцентиль переходит в `1 − перцентиль`, поэтому
при `PCT_LOW = 1 − PCT_HIGH` направления меняются местами, а уверенность
сохраняется до последнего бита. Симметрия здесь — свойство построения, а не
результат подбора порога.

**Способ объединения funding и OI не изменён** (ТЗ §3.2): направление по-прежнему
задаёт funding, OI остаётся подтверждением и множителем уверенности по той же
формуле `funding_conf × (0.4 + 0.6 × oi_factor)`, что была в `_trend_confidence`.
К open interest применено то же перцентильное правило (положение текущего OI в
своём недельном распределении вместо абсолютного «рост более 0.1 %»).

Окна берутся **за время**, а не «последние N строк», и прореживаются до одной
точки в час на стороне БД (`db.get_funding_window` / `get_open_interest_window`):
иначе при поминутной записи неделя давала бы более 10 000 строк на каждой
итерации агента.

### 1.4 Одно изменение, которое стоит отметить отдельно

`CONFIDENCE_SCALE` агента Futures изменён с `0.10` на `1.0`. Это **не** подбор
шкалы: прежнее значение было эмпирическим максимумом СТАРОЙ сырой величины
(отношение funding к порогу). Новая сырая уверенность нормирована по построению —
расстояние от границы нейтральной зоны, делённое на её ширину, умноженное на
множитель OI ≤ 1, то есть её максимум равен 1.0, как у Market Agent. Правило
«делим на максимум агента» не изменилось; изменилась измеряемая величина. Оставь
мы 0.10 — любая уверенность выше 0.1 схлопывалась бы в 1.0, и агент выдавал бы
константу. Параметр находится в коде, а не в `.env`, и в списке замороженных
параметров §7 отсутствует, но упоминается в нём по имени — поэтому изменение
вынесено сюда отдельным пунктом.

## 2. Блок B — калибровка вероятности

### 2.1 Что разделено

| Величина | Где хранится | Как считается | Как называется в интерфейсах |
|---|---|---|---|
| **Индекс согласия** | `signals.probability` (колонка НЕ переименована) | `\|балл\| × (0.5 + 0.5 × согласованность)` — **формула не изменена** | «Индекс согласия» |
| **Калиброванная вероятность** | `signals.calibrated_probability` | корзина кривой, построенной по фактическим исходам | «Вероятность успеха (по истории)» — только когда значение есть |

Правило, ради которого всё это делается: **система никогда не показывает число,
называя его вероятностью, если это число не выведено из фактических исходов.**
Пока кривой нет, поле `NULL`, и строки про вероятность просто не существует —
вместо неё не подставляется индекс согласия и не пишется «нет данных».

### 2.2 Схема

Миграция `db/migrations/007_calibration_inertia.sql`, откат —
`db/migrations/007_calibration_inertia_rollback.sql`. Применяется автоматически
при старте сервисов `decision` и `notify` (`db.ensure_calibration_schema`,
`db.ensure_signals_inertia`) и продублирована в `db/init.sql` для чистой
установки. Проверено локально на PostgreSQL 16: применение → повторное
применение → откат → повторное применение проходят без ошибок.

Уникальность активной кривой обеспечена частичным индексом
`idx_calibration_active ON calibration_curves (logic_version) WHERE is_active`;
попытка вставить вторую активную кривую той же версии отвергается базой (проверено).

### 2.3 Построение кривой

Модуль `src/calibration/` + точка входа `src/calibration_main.py`, сервис
`calibration` в профиле `tools` (как выгрузка Этапа 6.6.1). На хост pip-пакеты
не ставятся. Cron — 05:30 UTC, до суточной сводки в 06:00.

Алгоритм соответствует §4.3 дословно, с двумя местами, на которые стоит смотреть
внимательно:

1. **Прореживание до независимых наблюдений** — одно на непересекающееся
   4-часовое окно (границы 00/04/08/12/16/20 UTC), берётся первый по времени
   сигнал. Сделано дважды: запросом (`db.get_independent_outcomes`) и чистой
   функцией `to_independent`, чтобы правило было выражено кодом и покрыто тестом.
2. **Сглаживание к базовой ставке** `p = (successes + k·base_rate) / (n + k)`,
   `k = CALIBRATION_PRIOR_WEIGHT = 10`. Пустая корзина получает ровно базовую
   ставку.

**Монотонность не навязывается.** Изотоническая регрессия и любые методы,
предполагающие рост вероятности с ростом индекса, не применяются — и это
зафиксировано тестом `test_decreasing_dependence_is_preserved`: убывающая
зависимость проходит через построение кривой неискажённой. По данным 7.1
фактическая связь именно убывающая, и «выпрямление вверх» уничтожило бы
единственное, что данные показывают уверенно.

Нехватка данных — **штатное состояние**: кривая не строится, активная не
подменяется, в лог идёт «наблюдений X, требуется Y», код возврата 0.

### 2.4 Применение

* **Decision Agent**: индекс согласия → `probability` (как раньше); при наличии
  активной кривой → `calibrated_probability` и `calibration_id`, иначе обе NULL.
  Кривая читается из БД с кэшем в Redis (`calibration:active:<версия>`, TTL 1 ч).
  Сбой Redis или БД не роняет решение — сигнал сохраняется без вероятности.
* **Уведомления**: `NOTIFY_USE_CALIBRATED = false` — поведение не изменилось,
  отбор по индексу согласия и прежнему порогу 0.7. При `true` отбор идёт по
  калиброванной вероятности и порогу `NOTIFY_MIN_CALIBRATED = 0.55`; пока кривой
  нет, `calibrated_probability` у всех сигналов NULL, выборка пуста и
  **не уходит ничего** — проверено тестом.
* **Тексты**: «вероятность» → «индекс согласия» в уведомлениях, боте (`/last`,
  `/signal`, `/status`), суточной сводке. Строка «Вероятность успеха (по истории)»
  появляется только при непустой калиброванной вероятности и сопровождается
  датой кривой и размером её выборки.
* **Выгрузка**: колонка `probability` и её позиция сохранены, изменилась только
  подпись в заголовке листа («индекс согласия»). Новые колонки
  `calibrated_probability`, `calibration_id`, `inputs_hash`, `is_repeat`
  дописаны **в конец** — ранее выгруженные столбцы не сдвинулись (29 → 33).
  В Notion свойство базы «Вероятность %» не переименовывается (это поле базы, а
  не текст интерфейса); калиброванная вероятность и признак повтора добавлены в
  текст комментария.

## 3. Блок C — учёт инерции входов

`inputs_hash` — sha256 канонической строки
`агент:сигнал:уверенность(4 знака)`, агенты отсортированы по имени, `ts` не
входит. `is_repeat = true`, если хэш совпал с хэшем предыдущего по времени
сигнала того же инструмента.

Отправку уведомлений это **не фильтрует** — только делает статистику честной:
1440 решений в сутки при 24 обновлениях Market и 3 обновлениях funding — это не
1440 наблюдений. Повторы видны в суточной сводке («Из них повторных решений: X
(Y %)», «Уникальных наборов мнений: N»), в выгрузке (две новые колонки) и в боте
(`/status` и пометка в `/last`, `/signal`).

Все пять тестов из §5.4 ТЗ проходят (`tests/test_inertia.py`), плюс проверка
точного формата канонической строки из ТЗ.

## 6. Что делает заказчик

Команды выполняются подряд, без развилок. Git-команды идут через
`sudo -u agent`: каталог принадлежит пользователю `agent`, иначе git ответит
«dubious ownership».

### Шаг 1. Резервная копия БД (обязательно, до всего остального)

```bash
cd /opt/agent-trade
sudo -u agent /opt/agent-trade/scripts/backup_db.sh
```

Ожидается: свежий файл `.dump.gz` в `/opt/agent-trade/backups/`.

### Шаг 2. Обновление кода и пересборка стека

Первые две строки снимают дефект D-4 (репозиторий склонирован
`--depth 1 --branch`). Миграция применяется автоматически при старте сервисов.

```bash
cd /opt/agent-trade
sudo -u agent git remote set-branches origin '*'
sudo -u agent git fetch --unshallow origin || sudo -u agent git fetch origin
sudo -u agent git fetch origin main
sudo -u agent git checkout -B main origin/main
sudo -u agent docker compose up -d --build
```

Пересборка занимает несколько минут. Новые параметры `.env` (`LOGIC_VERSION`,
`FUTURES_*`, `CALIBRATION_*`, `NOTIFY_USE_CALIBRATED`, `NOTIFY_MIN_CALIBRATED`)
подставляются значениями по умолчанию из кода, поэтому существующий `.env`
править не нужно. Если хотите видеть их в файле явно — перезапустите установщик
(`sudo bash deploy/install.sh`), он допишет недостающие ключи и сохранит
имеющиеся значения.

### Шаг 3. Проверка развёртывания

```bash
cd /opt/agent-trade && sudo bash deploy/verify_7_3.sh
```

Печатает по пунктам: контейнеры, новые колонки, таблицу кривых, сигналы версии 4,
работу трёх агентов, наличие `bearish` у Futures **либо** объяснение по
фактическому распределению funding, заполнение `inputs_hash`, cron калибровки,
неизменность замороженных параметров. Ожидается «ИТОГ: ✅ проверки пройдены».

Строка «активной кривой нет» — **это норма** первые ~10 суток: кривая требует
60 независимых наблюдений (≈6 в сутки). До неё вероятность нигде не показывается.

### Шаг 4. Установить cron калибровки (если ставили не установщиком)

Если пункт 8 проверки показал 🔴:

```bash
sudo bash -c 'printf "# Этап 7.3 Калибровочная кривая — ежедневно 05:30 UTC\n30 5 * * * agent cd /opt/agent-trade \&\& /usr/bin/docker compose --profile tools run --rm --no-deps calibration >> /opt/agent-trade/logs/calibration.log 2>&1\n" >> /etc/cron.d/agent-trade'
```

Проверить построение кривой вручную можно в любой момент — это безопасно, при
нехватке данных ничего не меняется:

```bash
cd /opt/agent-trade && sudo -u agent docker compose --profile tools run --rm --no-deps calibration
```

## 7. Что этот этап НЕ делал

По §2 и §10 ТЗ: знак сигнала не переворачивался, веса агентов не подбирались,
таймфреймы, `DECISION_INTERVAL` и пороги уведомлений не менялись, колонка
`probability` не переименовывалась, уже записанные сигналы не пересчитывались,
методы с предположением монотонного роста не применялись, pip-пакеты на хост не
ставились, Market без доказанной асимметрии не трогался.

Отдельно: этот этап **не улучшает предсказательную способность** и не
претендует на это. Он устраняет структурный дефект одного агента, перестаёт
называть вероятностью величину, которая ею не является, и начинает честно
считать, сколько в потоке решений действительно новой информации. Ответ на
вопрос «стало ли ядро предсказывать лучше» даст повторная диагностика на данных
версии 4 — не раньше, чем накопится сравнимая выборка независимых окон.
