## §1. Почему Market Agent не даёт `bearish` на трёх токенах

### 1.1. Условия, при которых вывод становится `bearish`

`bearish` возвращается ровно тогда, когда **сумма пяти голосов отрицательна и не
погашена слабым трендом** (`src/agents/market.py:239-264`):

```python
votes["ema_stack"] = 1 if e_fast > e_mid > e_slow else (-1 if e_fast < e_mid < e_slow else 0)
votes["ema_slope"] = 1 if slope > 0 else (-1 if slope < 0 else 0)
votes["macd"]      = 1 if hist > 0 else (-1 if hist < 0 else 0)
votes["rsi"]       = 1 if rsi_val > 55 else (-1 if rsi_val < 45 else 0)
votes["di"]        = 1 if pdi > mdi else (-1 if pdi < mdi else 0)

score = sum(votes.values())
weak_trend = adx_val < 20 and abs(score) < 3
if score == 0 or weak_trend:   signal = neutral
else:                          signal = bullish if score > 0 else bearish
```

Отсюда два невыполняющихся условия-кандидата, и они различимы замером:
**либо `score` ни разу не уходит в минус** (какой-то из пяти голосов заперт в
плюсе), **либо `score` отрицателен, но гасится `weak_trend`** — при `ADX < 20`
и `|score| < 3` направление подменяется на `neutral`. Раздел 1B скрипта живого
замера показывает первое, раздел 1D — второе.

### 1.2. Зависимость от длины ряда — исключена замером

Один и тот же ценовой путь подан агенту усечённым до 223 свечей (столько у новых
токенов) и полным до 583 (столько у BTC):

```
=== C. Чувствительность к ДЛИНЕ РЯДА (уровень цены DOGE, 0.21) ===
  223 свечи (новые токены)   боковой   bullish=  85 bearish= 199 neutral= 117
  223 свечи (новые токены)   падающий  bullish=  35 bearish= 315 neutral=  51
  583 свечи (BTC)            боковой   bullish=  56 bearish= 214 neutral= 131
  583 свечи (BTC)            падающий  bullish=  25 bearish= 320 neutral=  56
```

На укороченном ряде `bearish` не просто достижим — на падающем рынке он
преобладает девятикратно. **Длина ряда причиной быть не может.**

### 1.3. Порог, зашитый под масштаб цены BTC, — НЕ НАЙДЕН

Один нормированный путь подан на пяти уровнях цены. Всё остальное совпадает до

### 1.5. Побочная находка: на дешёвых токенах умирает диагностика, а не решение

Один путь, два уровня цены, штатная `analyze_ohlcv`:

|---|---|---|

Решение совпадает до четвёртого знака — округление применяется **после** голосования

(`ema20/close - 1` и т.п.) либо повысить точность округления до значащих цифр,
а не до двух знаков. Пока этого нет, разбор ведётся по `votes` и `score` — они
целые и округление их не трогает.

### 1.6. Диагноз §1

Ни масштаб цены, ни длина ряда причиной не являются — оба исключены замером.
Значит невыполняющееся условие лежит **в самих данных токена**, и различить два
кандидата (запертый голос против гашения `weak_trend`) можно только на сервере.
Разбор даёт скрипт §4: таблица **1B** показывает, у какого из пяти голосов
столбец `minus` равен нулю, таблица **1C** — уходит ли `score` в минус вообще,
таблица **1D** — гасит ли `ADX < 20` направление.

Цифры по продакшну в этом отчёте не называются: продакшн-база из среды
исполнения недоступна, а называть цифру, полученную не измерением, запрещено §5.

## §2. Почему Futures Agent молчит — гипотеза ПОДТВЕРЖДЕНА и уточнена

### 2.1. Точное условие молчания

```python
n_funding = len(funding)
if n_funding < min_points:          # src/agents/futures.py:140
    return (SIGNAL_INSUFFICIENT, 0.0, {...}, ...)
```

`min_points = FUTURES_MIN_POINTS = 20` (`config.py:103`), окно
`FUTURES_LOOKBACK_HOURS = 168` ч (`config.py:98`).

### 2.2. Откуда берётся восьмичасовая сетка — измерено по установленной ccxt

Гипотеза «funding приходит раз в 8 часов» **подтверждена не документацией, а
кодом библиотеки**. В ccxt 4.4.100 `okx.parse_funding_rate` возвращает:

```python
'timestamp': None,
'fundingTimestamp': fundingTime,      # fundingTime — сетка расчётов, 8 ч
```

Коллектор выбирает метку так (`src/collectors/futures.py:46`):

```python
ts = _ms_to_dt(data.get("timestamp") or data.get("fundingTimestamp"))
```

`timestamp` равен `None` → берётся `fundingTimestamp`. Дальше `insert_funding`
делает UPSERT по первичному ключу `(instrument_id, ts)` (`db/init.sql:89-94`),
поэтому все опросы внутри одного расчётного периода схлопываются в **одну
строку**. Итог: **ровно три строки funding в сутки на контракт**, независимо от
`FUTURES_INTERVAL`.

Прореживание в `get_funding_window` до одной точки в час (`db.py:336-343`) здесь
ни на что не влияет — строки и так стоят с шагом 8 часов.

### 2.3. Расчётная дата перехода порога

Двадцать точек на восьмичасовой сетке охватывают **(20 − 1) × 8 = 152 часа =
6 суток 8 часов**. Это и есть возраст, с которого контракт перестаёт молчать:

```
дата перехода = первая запись funding по контракту + 152 часа
```

Формула проверена на локальной базе: контракт с первой записью
`2026-08-23 00:00 UTC` даёт `2026-08-29 08:00 UTC` — ровно то, что печатает
столбец `threshold_at` раздела 2B скрипта.

При заведении токенов 22–23.08 расчётная дата попадает в **28.08 – 29.08.2026**;
точный час зависит от того, на какой расчёт пришлась первая запись, и берётся из
таблицы 2B — здесь он **не измерен**, потому что первые метки funding лежат в
продакшн-базе.

Запас над порогом мал: окно вмещает 21–22 точки сетки при требуемых двадцати,
поэтому выпадение двух-трёх записей вернёт в молчание и зрелый контракт. Граница
зафиксирована тестами `test_futures_boundary_*`.

### 2.4. Почему полтора суток молчания не дали ни одного оповещения

Измерено по коду, и это **три независимых причины сразу**:

1. **`insufficient_data` не бросает исключения.** `_record_failure` вызывается
   только из блоков `except` (`base.py:184`, `base.py:194`), поэтому штатный
   «данных нет» в `agent_failures` не попадает никогда. Так и задумано:
   различать «данных нет» и «агент сломался» — сознательное решение Этапа 7.2.
2. **Механизм пустых выборок не срабатывает.** Он есть, но проверяет
   `is_empty=(not funding and not oi)` (`futures.py:251`). У молодого контракта
   выборка **не пуста** — в ней шесть точек вместо двадцати, — поэтому счётчик
   `_empty_read_streak` сбрасывается и авто-сброс не запускается.
3. **Ни вотчдог, ни суточная сводка про `insufficient_data` не знают вовсе.**

   ```
   $ grep -c 'insufficient' scripts/watchdog.py src/health/daily_report.py
   scripts/watchdog.py:0
   src/health/daily_report.py:0
   ```

**Диагноз:** молчание агента на четырёх токенах из пяти — не сбой, и отсутствие
записи в `agent_failures` задумано. Но **отсутствие оповещения не задумано, а
просто не предусмотрено**: ни одна из трёх подсистем надзора не смотрит на долю
`insufficient_data` по инструментам.

**Рекомендация (не правка):** добавить в суточную сводку строку «доля
`insufficient_data` по агенту и инструменту за сутки» и порог, выше которого она
попадает в алерт. Это надзор, а не логика агента, — правкой Этапа 8.5 не
является и в §3 не входит.

## §3. Ложная тревога в `diagnose_8_4.sh` — исправлено

### Причина, измеренная

В проде `stdout` не TTY, поэтому structlog пишет `JSONRenderer`
(`src/core/logging.py:36-41`), а он экранирует кириллицу:

```
$ python3 -c "<рендер настоящей строкой structlog>"
как журнал это хранит:
  {"event": "Служебные листы …", "windows": 94, "horizons_h": [1, 4, 12, 24]}
ищется ли "Служебные листы" подстрокой: False
ищется ли horizons_h: True
после json.loads: Служебные листы пересобраны
```

Контроль на **исправном** журнале, собранном настоящим рендерером:

```
КОНТРОЛЬ — прежняя проверка на ИСПРАВНОМ журнале:
  🔴 НЕ нашла → объявила бы блокирующую находку (ложная тревога)
  строк, найденных grep по русскому тексту: 0
  строк, найденных grep по ключу horizons_h: 1
```

Второй дефект того же раздела: строки листа подписывались как «отказы», хотя
успешно принятая пачка несёт `level = info`:

```
  разбор: Sheets: пачка принята | лист: Независимые окна | уровень: info
прежняя подпись назвала бы эти строки «отказами листа», хотя level = {'info'}
```

### Что сделано

Раздел C теперь разбирает журнал как JSON, признак версии берёт машиночитаемым
ключом `horizons_h`, а отказы считает по `level == "error"`, а не по имени листа.
Проверено на двух собранных настоящим `JSONRenderer` журналах:

```
=== журнал: export_ok ===
  🟢 ключ horizons_h в журнале есть — писавший код не старше Этапа 8.1
    записей уровня error за всё время журнала: 0
  🟢 записей уровня error в журнале нет

=== журнал: export_bad ===
  🔴 БЛОКИРУЮЩЕЕ: ключа horizons_h в журнале нет…
    записей уровня error: 1
      {"timestamp": "…", "event": "Ошибка выгрузки в Sheets", "error": "лист «Независимые окна»: ok=false"}
```

### Правило, зафиксированное

> **Проверка, ищущая текст в журнале, обязана искать его в том виде, в каком
> журнал его хранит.** Практически: либо разобрать строку как JSON и сравнивать
> уже раскодированный текст, либо искать машиночитаемый ключ (`horizons_h`,
> `level`), который лежит в файле как есть. Искать русский текст подстрокой в
> JSON-журнале нельзя — совпадений не будет никогда.
>
> Следствие: «ничего не найдено» само по себе не находка. Проверка обязана
> отличать «признака нет» от «искать не умеем».

Правило закреплено тестами `test_log_*` в `tests/test_stage_8_5.py`.

## §4. Скрипт живого замера

`deploy/diagnose_8_5.sh` — только чтение, одна команда, вызывается файлом из
репозитория и не зависит от попадания в образ (SQL идёт в `psql` через stdin,
Python — через `python -c`).

```bash
sudo -u agent bash /opt/agent-trade/deploy/diagnose_8_5.sh
```

Разделы: **0** — действующие пороги из контейнера, а не из `.env.example`;
**1A** — распределение выводов Market по токенам; **1B** — голоса с колонкой
`minus` (нуль в ней и есть невыполняющееся условие); **1C** — распределение
`score`; **1D** — гашение слабым трендом; **1E** — движение цены рядом с
распределением решений; **1F** — глубина часового ряда; **2A** — выводы Futures;
**2B** — ряд funding с расчётной датой перехода порога; **2C** — открытый
интерес; **2D** — `agent_failures` и сверка «молчаний против записей об отказах».
Итог разделяет блокирующие находки и требующие внимания и завершается одной
строкой действия.

Проверка перед выдачей: `bash -n` чист, **14 из 14** запросов выполнены на
локальном PostgreSQL 16, поднятом из `db/init.sql` и всех миграций, на данных,
повторяющих форму продакшна. Разбор голосов на этих данных показал ровно то, для
чего сделан: у отстающих токенов столбец `minus` равен нулю.

**Оговорка §5:** локальный прогон доказывает работоспособность запросов, а не
поведение на сервере. Цифры продакшна даст только запуск на сервере.
